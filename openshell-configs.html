OpenShell configs

Configs and notes for running AI coding agents (Claude Code, OpenCode, Antigravity CLI) in NVIDIA OpenShell sandboxes with Podman, editing their files in VS Code, and moving code in and out.

TL;DR

OpenShell runs AI coding agents in locked-down sandboxes. Agents get only the network access and credentials you allow, and API keys and tokens never enter the sandbox.

Concepts

  • Gateway - the local OpenShell server (https://localhost:17670) that manages everything below. It runs as a background service and starts sandboxes through a container runtime (here Podman).
  • Supervisor - the OpenShell process that runs next to each sandbox's workload, on the trusted side. It makes every policy decision, adds the real credentials to allowed requests and reports to the gateway; the agent itself has no network except its channel to the supervisor.
  • Profile - a template for a type of provider: which credential it needs (e.g. CLAUDE_CODE_OAUTH_TOKEN), which hosts it may reach, and which binaries may use it. A YAML file in providers/, imported into the gateway. See Provider profiles.
  • Provider - an instance of a profile that holds your actual key or token, stored in the gateway. OpenShell's network proxy adds the credential to outgoing requests to the allowed hosts, so the agent never sees it. Antigravity CLI can't use one and logs in inside the sandbox instead; see Two ways to sign in for the trade-offs.
  • Image - the container image a sandbox starts from. It must contain the agent, e.g. claude-sandbox or opencode-sandbox, built from the folders in images/.
  • Sandbox - a running, isolated container created from an image, with one or more providers attached, running a main command. The sandbox stops when that command exits.
  • Policy and rules - what a sandbox may access. A policy file sets filesystem access (and can add network rules), providers add network access, and you approve or reject further network rules as the agent gets blocked. See Sandbox policies.

Basic steps

  1. Set up Podman and install OpenShell.
  2. Store your key or token in the Keychain (or in .env, or another secrets manager).
  3. For an agent (Claude Code or OpenCode): import its profile, create a provider (bin/provider.sh claude or bin/provider.sh opencode does both), build its image (make images builds all of them). Antigravity CLI needs only its image; you log in inside the sandbox.
  4. Start and use a sandbox, with the agent in your terminal or with VS Code. By hand (for OpenCode: image opencode-sandbox:latest, provider openrouter, agent opencode): Once, create a sandbox that keeps running:
openshell sandbox create --name my-task --from claude-sandbox:latest --provider claude \
  --policy policies/vscode-terminal.yaml --detach -- sleep infinity

Then, as often as you like, start the agent in this terminal, or open the sandbox in VS Code:

openshell sandbox exec my-task --workdir /sandbox -- claude-start
openshell sandbox connect my-task --editor vscode

Or with the script, which creates the sandbox on first use. The first line starts the agent in this terminal, the second opens the same sandbox in VS Code:

bin/sandbox.sh claude my-task
bin/sandbox.sh claude my-task --vscode

The first argument is a profile: claude, opencode, agy, or a variant such as browser, hyperframes, graphics or kirocrew (see profiles/). bin/sandbox.sh without arguments lists them. 5. In VS Code, start the agent in the integrated terminal (claude-start, opencode or agy). 6. Open a shell in the sandbox when you need one, with sandbox exec or plain SSH:

openshell sandbox exec my-task --workdir /sandbox -- bash

For SSH, add the host entry once (it's already there after a --editor vscode connect), then connect:

openshell sandbox ssh-config my-task >> ~/.ssh/config
ssh openshell-my-task.default
  1. Move code in and out with git bundles, then review, push and open the MR from your machine. in puts the repo in /sandbox/myrepo on branch agent/my-task, and out brings the agent's commits back as branch agent/my-task:
bin/bundle.sh in  my-task ./myrepo
bin/bundle.sh out my-task ./myrepo

For single files, use upload and download. The destination is a folder, and the file keeps its name, here /sandbox/notes.md and ./report.html (see Single files):

openshell sandbox upload   my-task ./notes.md /sandbox
openshell sandbox download my-task /sandbox/report.html .
  1. Approve or reject network rules when the agent gets blocked. bin/watch-denied.sh shows what is being blocked, live, across all sandboxes (see Watching denials).

Optional

Not needed for the basic steps above. Each one gives the agent more reach, so add it when a task needs it.

MCP servers and ACP

  • Remote MCP servers (HTTP): add them in the agent as usual and allow them with a protocol: mcp rule, which can limit the methods and tools. Tokens go in a provider, never in the policy. See Example policy with network rules.
  • Local MCP servers (stdio, e.g. as container images): a sandbox can't run containers, so run the server on the host behind an HTTP bridge and use it like a remote server, by the host's IP. Its secrets stay on the host. See MCP servers in containers on the host.
  • ACP: to drive the agent from a UI on the host, bin/sandbox.sh claude|opencode|agy my-task --acp runs its ACP server over stdin/stdout, without opening a port. agy has no ACP mode of its own, so its image carries a community adapter; log in to the sandbox once first. To try it, chat with bin/acp_client.py connect my-task. See ACP.

Headless browser use

  • What: Claude Code uses a headless Chromium inside the sandbox, through Playwright MCP. The browser has none of your logins.
  • How: build the claude-browser image, list the sites the browser may open in policies/browser.yaml, and start with bin/sandbox.sh browser.
  • What limits it: OpenShell decides which sites the browser can reach, the same way as for any other program. Any page the browser opens can receive data in its URL, so the list of sites is what keeps data in.
  • Local pages: a dev server in the sandbox (localhost) works without a rule.
  • Don't let the agent use your own Chrome.
  • See Headless browser use.

HyperFrames (videos from HTML)

  • What: Claude Code makes videos with HyperFrames in the sandbox, with its skills, FFmpeg and headless Chromium, and you watch and edit in HyperFrames Studio in your own browser.
  • How: make claude-hyperframes, then bin/sandbox.sh hyperframes (it forwards port 3102), ask for the preview on port 3102, and open http://127.0.0.1:3102.
  • What limits it: policies/hyperframes.yaml allows only read-only access to the script and font CDNs and the HyperFrames registry. The Studio page runs in your browser, outside the sandbox (see below).
  • With Antigravity CLI: bin/sandbox.sh agy-hyperframes uses the agy-hyperframes image (HyperFrames and a browser too). Its policy lets the processes that can read agy's login tokens reach the CDNs, so use it for that work only.
  • See HyperFrames.

Graphics (vector art and photo editing)

  • What: Claude Code draws and exports SVG and PDF with VectorCraft and edits photos with PhotoCraft, two open-source ArtCraft apps, through their headless CLIs and MCP servers in the sandbox. The image includes the clean-vector-from-raster skill (photo to print-ready SVG), Python 3 and uv (packages from PyPI), and graphics-gallery, a web page for browsing the images. With a Replicate token it can also generate images and video with hosted models (MCP server and skills).
  • How: make claude-graphics, then bin/sandbox.sh graphics, open http://127.0.0.1:3102 (the gallery starts with the agent, and the script forwards its port), and openshell sandbox download the results.
  • What limits it: policies/graphics.yaml is the terminal policy plus read-only access to PyPI for python3 and uv, and the MCP servers can only read and write below /sandbox. For Replicate (bin/provider.sh replicate) the token goes only to api.replicate.com, plus read-only rules for its output, streaming and docs hosts.
  • See Graphics.

Kiro Crew (persistent agent workspace over ACP)

  • What: Kiro Crew runs its own gateway and web dashboard inside the sandbox, driving Claude Code over the Agent Client Protocol as its agent harness. Apps from its app store (todo lists, dashboards, and so on) run their own backends in the sandbox and render in your browser.
  • How: make claude-kirocrew, then bin/sandbox.sh kirocrew, open the dashboard link it prints with 127.0.0.1 in place of localhost. bin/sandbox.sh kirocrew-readonly is the same image with no network access, for work that doesn't need the app store.
  • What limits it: policies/kirocrew.yaml allows Kiro Crew's updates, its app store, clone-only GitHub access and the PyPI/npm registries. Apps are third-party code that runs in the sandbox.
  • Known gaps: Kiro Crew's Remote Crew (reaching this sandbox from another Kiro Crew over SSH) does not work under OpenShell. See Kiro Crew for why and the workaround.
  • See Kiro Crew.

Logs and OpenTelemetry

  • What: keep the sandboxes' security events (every allowed and denied connection, HTTP request and SSH session), or send them to a log backend, as OpenTelemetry logs.
  • How: turn on OpenShell's structured log once, then export to a file or push to an OTLP endpoint, and look at the events with the small terminal viewer:
openshell settings set --global --key ocsf_json_enabled --value true --yes
  • To a file: bin/otel-export.py --out sandboxes.otlp.jsonl
  • Live, to a collector: bin/otel-export.py --endpoint http://localhost:4318/v1/logs --follow
  • Live, in the terminal: bin/otel-export.py --out - --follow | bin/otel-view.py
  • Careful where you send them: the events show what the agent did (hosts, URLs, process names).
  • See Logging and metrics.

Gateway metrics

  • What: the gateway's own numbers: connected sandboxes, relays into sandboxes (exec, connect, SSH, port forwards), and API calls with latency and errors. Not what agents do (that's in the logs above), and not CPU or memory (podman stats).
  • How: turn on the Prometheus endpoint once (restarts the gateway), then view a summary in the terminal. -w refreshes it every 5 seconds; without it, it prints once:
echo 'OPENSHELL_METRICS_PORT=9464' >> ~/.config/openshell/gateway.env
brew services restart openshell
bin/metrics-view.py -w
  • For history and graphs, scrape http://127.0.0.1:9464/metrics with Prometheus, or send the metrics to an OpenTelemetry backend together with the logs, with the Collector configs in observability/. To browse and graph both locally, see Viewing in Grafana.

Viewing a web page in your browser

  • What: view a web page the agent serves in your own browser.
  • How: the agent runs a server on a port in the sandbox, and you forward the port. After start, open http://127.0.0.1:3000:
openshell forward start 3000 my-task -d
openshell forward stop  3000 my-task
  • This adds risk: the page is the agent's code, and in your browser it runs outside the sandbox, with your network access. It can reach other services on your machine, send data to any site, and use your browser's logins.
  • So: only do it when you need to, and open the page in a private window.

If something fails, see Troubleshooting.

OpenShell concepts

A visual tour of how OpenShell works: the parts, how a request from an agent is checked, and which setting controls what. Every command on this page is an openshell command; the helper scripts in bin/ are left out, so you see what OpenShell itself does. Diagrams follow the page's light/dark theme.

The big picture

OpenShell runs an AI coding agent inside a sandbox: a container where the filesystem is restricted, the only way out is a policy-checking proxy, and API keys exist only as placeholders. A gateway on your machine manages the sandboxes, the credentials and the policies.

  1. You talk to the gateway with the openshell CLI, an editor over SSH, or a forwarded port. You never talk to a sandbox directly.
  2. The gateway creates the sandbox through Podman (or Docker, a MicroVM, Kubernetes): a workload container from your image, and a supervisor next to it. The supervisor connects out to the gateway and gets the policy and the provider credentials.
  3. The agent runs in the workload. Its files are limited to the paths in the policy, it runs as a non-root user, and its API key is only a placeholder. Its only way out is a private channel to the supervisor.
  4. The supervisor decides on every connection. If the host, program and request are allowed, it opens the real connection and adds the real key.
  5. Everything else is refused and logged, and OpenShell drafts a rule you can approve if it was legitimate.

Zoomed out, the agent is boxed in several times. The outermost layers belong to the container runtime; the innermost are OpenShell's own.

How the objects fit together

Four things combine into a sandbox. A profile is a template, a provider is an instance of it that holds a secret, the image contains the agent, and the policy sets filesystem access and extra network rules.

# 1. Import the profile (once), and create a provider from it with your token
openshell provider profile lint   -f providers/claude-code-oauth.yaml
openshell provider profile import -f providers/claude-code-oauth.yaml
openshell provider create --name claude --type claude-code-oauth --from-existing

# 2. Create a sandbox from an image, with the provider and a policy
openshell sandbox create --name my-task --from claude-sandbox:latest \
  --provider claude --policy policies/vscode-terminal.yaml \
  --detach -- sleep infinity

# 3. See what exists
openshell provider profile list
openshell provider list
openshell sandbox list

Sandbox lifecycle

openshell sandbox create --name my-task --from claude-sandbox:latest \
  --provider claude --detach -- sleep infinity
openshell sandbox list                      # wait for Ready
openshell sandbox exec my-task --workdir /sandbox -- bash
openshell sandbox stop  my-task             # keeps the workspace
openshell sandbox start my-task
openshell sandbox delete my-task

Credentials never enter the sandbox

The agent gets an environment variable that looks like a key but is a placeholder (openshell:…). The real value stays in the gateway. When the agent sends a request, the supervisor checks it, and only then swaps the placeholder for the real credential, in headers, Basic auth, query parameters or URL paths (and, if the profile opts in, request bodies).

The profile defines this contract. This excerpt of claude-code-oauth says which secret, where it goes, and who may use it:

id: claude-code-oauth
credentials:
  - name: oauth_token
    env_vars: [CLAUDE_CODE_OAUTH_TOKEN]   # read once from the host by --from-existing
    auth_style: bearer                    # sent as "Authorization: Bearer ..."
    header_name: authorization
endpoints:                                # the credential is added ONLY on these
  - host: api.anthropic.com
    port: 443
    protocol: rest
    access: read-write
    enforcement: enforce
binaries:                                 # only these programs may use it
  - /usr/local/lib/node_modules/@anthropic-ai/**
openshell provider profile describe claude-code-oauth
openshell provider list
openshell provider update claude --from-existing   # rotate the token

What a sandbox may access

Access comes from three sources, added together. Filesystem rules are fixed when the sandbox starts; network access can change while it runs.

1 · Policy file: filesystem

Which paths processes may read or write. Enforced by Landlock in the kernel.

openshell sandbox create \
  --policy my.yaml ...

Fixed at creation. Changing it means a new sandbox.

2 · Providers: hosts + credentials

Each attached provider allows the hosts in its profile and adds its credential to requests to them.

openshell sandbox create \
  --provider claude ...

Set by the attached providers. Editing a profile reaches running sandboxes at their next sync.

3 · Network rules: extra hosts

Per-binary rules in the policy's network_policies, and rules you approve after a denial.

openshell policy set my-task \
  --policy x.yaml --wait
openshell rule approve \
  my-task --chunk-id ID

Live. Applies to a running sandbox, without a restart.

How a connection is decided

Every connection from inside the sandbox goes through the proxy. It asks the same questions in the same order, and the first “no” ends the connection.

Anatomy of a network rule

A rule says who may reach where, and what they may do there.

WHO · binaries

The program that opens the connection, by its real path. For npm that is node; for git over HTTPS it is git-remote-http. Child processes are covered too.

binaries:
  - path: /usr/local/bin/node
WHERE · endpoints

Host, port and, for MCP, a path. Wildcards are allowed.

endpoints:
  - host: registry.npmjs.org
    port: 443
WHAT · protocol

With protocol: rest each HTTP request is checked: a preset, or exact methods and paths. protocol: mcp checks MCP methods and tool names.

    protocol: rest
    access: read-only      # GET HEAD OPTIONS
    enforcement: enforce   # audit = log only

Finer control with rules and deny_rules (this is how git clone is allowed but git push is not):

network_policies:
  github_clone:
    name: github-clone
    endpoints:
      - host: github.com
        port: 443
        protocol: rest
        enforcement: enforce
        rules:                                  # allowed
          - allow: { method: GET,  path: "/**/info/refs", query: { service: git-upload-pack } }
          - allow: { method: POST, path: "/**/git-upload-pack" }
        deny_rules:                             # always wins
          - { method: "*", path: "/**/git-receive-pack" }
    binaries:
      - path: /usr/lib/git-core/git-remote-http

For a remote MCP server, OpenShell reads each request and checks the method and, for tools/call, the tool name (the tool's arguments are not checked):

  huggingface_mcp:
    endpoints:
      - host: huggingface.co
        port: 443
        path: /mcp
        protocol: mcp
        enforcement: enforce
        mcp: { versions: ["2025-03-26", "2025-06-18", "2025-11-25"], allow_all_known_mcp_methods: true }
        rules:       [ { allow: { tool: "hub_repo_*" } } ]   # only these tools
        deny_rules:  [ { method: tools/call, tool: hf_fs } ]  # never this one
    binaries:
      - path: /usr/local/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe

Changing network access while it runs

Network access starts tight and is widened on purpose. Two ways: approve what the agent was denied, or push a changed policy. OpenShell drafts a rule from every blocked connection; the policy prover flags risky ones (a credential reaching a new host, cloud-metadata addresses, a new HTTP method on a credentialed host). Auto-approval is off by default, and an agent can only propose rules itself if you turn on agent_policy_proposals_enabled. Every change is a new numbered, hashed policy version, so you can see what changed and when.

# Review and decide on what was denied
openshell logs my-task | grep DENIED
openshell rule get     my-task --status pending
openshell rule approve my-task --chunk-id <chunk-id>
openshell rule reject  my-task --chunk-id <chunk-id> --reason "Not needed for this task."
openshell rule approve-all my-task              # or: rule clear my-task

# See the history and what is in force
openshell policy list my-task
openshell policy get  my-task --full            # with the providers' network rules
openshell rule history my-task

# Push a changed policy to a running sandbox (hot reload)
openshell policy get my-task --base | sed -n '/^version:/,$p' > policy.yaml   # edit network_policies, keep filesystem_policy
openshell policy set my-task --policy policy.yaml --wait

# Or add a single endpoint, without editing a file
openshell policy update my-task --add-endpoint docs.python.org:443:read-only:rest:enforce \
  --rule-name python-docs --binary /usr/local/bin/node --dry-run     # preview first
openshell policy update my-task --remove-rule python-docs --wait

# One policy for every sandbox
openshell policy set --global --policy policy.yaml --yes
openshell policy delete                         # remove the global lock

Filesystem policy

The filesystem part of the policy is a list of paths. Everything not listed is unreachable for the agent and its tools. The kernel enforces it (Landlock), so no program in the sandbox can opt out.

version: 1
filesystem_policy:
  include_workdir: true          # /sandbox is read-write
  read_only:  [/bin, /usr, /lib, /proc, /dev/urandom, /etc, /var/log]
  read_write: [/tmp, /dev/null, /dev/pts, /dev/ptmx]
landlock:
  compatibility: best_effort     # if Landlock can't be applied the sandbox runs WITHOUT these rules; hard_requirement refuses to start
openshell policy get my-task --base      # the policy the sandbox got
openshell policy get my-task --full      # including the network rules from its providers

Reaching a sandbox

A sandbox opens no port. Everything you do with it travels through the gateway: your commands in, the agent's pages out, files both ways.

openshell sandbox exec my-task --workdir /sandbox -- bash            # a shell
openshell sandbox exec my-task -- ls -la /sandbox                    # one command
openshell sandbox connect my-task --editor vscode                    # VS Code over SSH
openshell sandbox ssh-config my-task >> ~/.ssh/config                 # then: ssh openshell-my-task.default

openshell sandbox upload   my-task ./spec.md /sandbox                # lands in /sandbox/spec.md
openshell sandbox download my-task /sandbox/myrepo/report.html .

openshell forward start 3000 my-task -d        # http://127.0.0.1:3000 shows the sandbox's port 3000
openshell forward list
openshell forward stop 3000 my-task

openshell service --help                        # publish a service through the gateway under its own URL

Seeing what happens

The supervisor records every allowed and denied connection, every checked HTTP request, SSH sessions and policy changes. You choose how to read them.

openshell logs my-task                       # last 200 lines
openshell logs my-task --tail                # follow live
openshell logs my-task | grep DENIED         # what was blocked, and by which binary
openshell settings get --global              # effective settings
openshell settings set --global --key ocsf_json_enabled --value true --yes

Setup

Podman

OpenShell runs the sandboxes in a container runtime. These steps use Podman (5.x is required). OpenShell can also use Docker (28.0 or later) or MicroVMs.

macOS (Apple Silicon)

On macOS, Podman runs containers in a Linux VM called a Podman machine. Note that NVIDIA's support matrix lists macOS on Apple Silicon only with Docker Desktop, and Podman as supported for rootless Linux workstations. Podman on a Mac works with the steps here (they are what this repo is tested with), but it is outside that matrix.

  • Install Podman, either with the installer from podman.io (the Podman docs recommend this) or with Homebrew:
brew install podman
  • Create and start the Podman machine:
podman machine init
podman machine start
  • Verify the version is 5.x and that containers run:
podman --version
podman run --rm quay.io/podman/hello

Linux

Podman on Linux needs cgroups v2 and an active Podman user socket.

  • Install Podman, e.g. sudo apt install podman or sudo dnf install podman
  • Start the user socket, and enable it so it starts at login:
systemctl --user enable --now podman.socket
  • Check that cgroups v2 is used (should print v2):
podman info --format '{{.Host.CgroupsVersion}}'

Install OpenShell

  • Run the installer. It installs the CLI, the policy prover and a local gateway. On macOS it uses Homebrew and runs the gateway as a Homebrew service at https://localhost:17670. On Linux it runs as a systemd user service.
curl -LsSf https://raw.githubusercontent.com/NVIDIA/OpenShell/main/install.sh | sh

Use Podman for the gateway

If you don't set a driver, the gateway auto-detects one. It tries Kubernetes first, then Podman, then Docker. To make sure it uses Podman, set the driver in ~/.config/openshell/gateway.toml:

[openshell.gateway]
compute_driver = "podman"

The gateway finds the Podman socket by itself, including the podman machine socket on macOS.

  • Validate the config, then restart the gateway:
openshell-gateway config preflight --path ~/.config/openshell/gateway.toml

On macOS:

brew services restart openshell

On Linux:

systemctl --user restart openshell-gateway

Verify the installation

openshell status
  • If something is wrong, check the gateway service: brew services list on macOS, or journalctl --user -u openshell-gateway -f on Linux
  • Quick test with the default sandbox image (a minimal Ubuntu without an agent):
openshell sandbox create --name demo

Credentials

A provider's key or token is only needed on the host once: when you create the provider (and again when you rotate the token). After that it's stored in the gateway, and the sandbox only ever sees a placeholder. So the question is where the key lives on your machine until you create the provider, and in between rotations.

bin/provider.sh looks for the credential in this order, and uses the first one it finds:

  1. The environment, e.g. set by another secrets manager for that one command (see Other secrets managers)
  2. The macOS Keychain (recommended)
  3. .env in this folder (fallback)

It tells you which one it used, never prints the value, and passes it to openshell in the environment of a subshell, never on a command line (where ps would show it).

Agent Variable Where to get it
Claude Code CLAUDE_CODE_OAUTH_TOKEN claude setup-token on the host, see Create an OAuth token
OpenCode OPENROUTER_API_KEY openrouter.ai/keys
Replicate (graphics profile, optional) REPLICATE_API_TOKEN replicate.com/account/api-tokens, see Replicate

In the Keychain (recommended)

Store the key as a generic password with service openshell and the variable name as account. -w without a value makes security prompt for it, so it doesn't end up in your shell history, and -U replaces an existing one:

security add-generic-password -U -s openshell -a CLAUDE_CODE_OAUTH_TOKEN -w
security add-generic-password -U -s openshell -a OPENROUTER_API_KEY -w
security add-generic-password -U -s openshell -a REPLICATE_API_TOKEN -w

Then create the provider with bin/provider.sh claude (or opencode, or replicate), and after a new token with bin/provider.sh --update claude.

  • Check that it's there, without showing it: security find-generic-password -s openshell -a CLAUDE_CODE_OAUTH_TOKEN >/dev/null && echo found
  • Remove it: security delete-generic-password -s openshell -a CLAUDE_CODE_OAUTH_TOKEN
  • Items created with security can be read back by security without a prompt, as long as your login keychain is unlocked. To be asked every time, open the item in Keychain Access and remove security from Access Control.

In .env (fallback)

If you're not on macOS, or prefer a file, put the keys in .env in this folder. Start from the template; .env is ignored by git (see .gitignore):

cp .env.example .env
chmod 600 .env

Then fill in the values, e.g. CLAUDE_CODE_OAUTH_TOKEN=sk-ant-oat01-.... bin/provider.sh refuses a .env that others can read or write, and reads only the one line it needs instead of running the file as shell code.

Why .env isn't preferred:

  • It's a plaintext copy that outlives its use. The gateway already holds the key after provider create, but .env keeps another copy in your project folder for as long as the token is valid (a year for claude setup-token).
  • Anything running as you can read it. chmod 600 only keeps out other users. Your editor and its extensions, an agent running on the host, build tools, npm install scripts and malware all run as you. The Keychain encrypts the key and only hands it out while you're logged in, and can be set to ask first.
  • It spreads. Backups (Time Machine, cloud sync of the folder), zip or rsync of the project, and copies like .env.bak or .env.old all carry the key in plaintext. .gitignore only protects against git add, and one mistake there (a renamed file, git add -f, a different repo's .gitignore) publishes the key.
  • It's easy to show by accident. cat, a screen share, or an AI assistant asked to "look at the config" reads it just like any other file.
  • Loading it is error-prone. A plain source .env doesn't export the variables, and set -a; . ./.env in your main shell leaves the keys in its environment, where every program you start later gets them. Sourcing also runs the file as shell code.

If you do use .env, delete it once the provider is created, or keep the key in a password manager and only paste it in when you need it.

Other secrets managers

Any secrets manager works, because the environment comes first: let the manager set the variable for just the one command, and bin/provider.sh uses it. For example:

  • 1Password CLI. .env.tpl holds references, not secrets, e.g. CLAUDE_CODE_OAUTH_TOKEN=op://Private/Claude setup-token/credential:
op run --env-file=.env.tpl -- bin/provider.sh claude
  • Bitwarden Secrets Manager:
bws run -- bin/provider.sh claude
  • Linux Secret Service (GNOME Keyring, KWallet), pass, or anything else that prints the secret:
CLAUDE_CODE_OAUTH_TOKEN="$(secret-tool lookup service openshell account CLAUDE_CODE_OAUTH_TOKEN)" bin/provider.sh claude
CLAUDE_CODE_OAUTH_TOKEN="$(pass show openshell/claude)" bin/provider.sh claude

VAR=value command sets the variable only for that command, so it doesn't stay in your shell. The same works with team vaults such as HashiCorp Vault (vault kv get -field=...), AWS Secrets Manager or Azure Key Vault, which also give you access logs and central rotation.

Token expiry

claude setup-token tokens are valid for a year. To have OpenShell track that, set the expiry on the provider, e.g. a year from the day you created the token:

openshell provider update claude --credential-expires-at oauth_token=2027-10-11T00:00:00Z

To rotate: create a new token, store it (security add-generic-password -U ... replaces the old one), and run bin/provider.sh --update claude. Running sandboxes pick up the new credential for new processes.

Agents

The agent chapters follow the same steps: profile, provider, image, sandbox. Antigravity CLI is the exception: it has no provider, and you log in inside the sandbox. The next section explains the difference.

Two ways to sign in: provider or login in the sandbox

The agents here use one of two ways to get at your account. Which one an agent can use depends on the agent, not on a choice in this repo.

Credential in a provider (Claude Code, OpenCode). You create the credential on the host (claude setup-token, an OpenRouter API key) and store it in a provider in the gateway. The sandbox only gets a placeholder in an environment variable, e.g. CLAUDE_CODE_OAUTH_TOKEN=openshell:resolve:env:.... When the agent sends a request with the placeholder to a host in the profile, OpenShell's proxy swaps in the real value on the way out. The profile also says which binaries may do that.

Login in the sandbox (Antigravity CLI). The agent runs its own OAuth login inside the sandbox and keeps the tokens there, like it would on your Mac. There's no provider; a sandbox policy (policies/antigravity.yaml) opens the Google hosts it needs.

Provider (Claude Code, OpenCode) Login in the sandbox (Antigravity CLI)
Where the secret is In the gateway. The sandbox has a placeholder that's useless anywhere else In the sandbox (/sandbox), including a long-lived refresh token
What the agent can do with it Use it through the proxy, only on the hosts in the profile and only from the listed binaries Read it, and send it anywhere the sandbox can reach
If the sandbox is compromised The token can't be taken out; nothing to rotate Assume the token is taken: log out, delete the sandbox, revoke the login in your Google account
Network access From the provider's profile From the sandbox policy, which you have to keep narrow
Setup Once, on the host: create the token or key, bin/provider.sh Once per sandbox: open the login link, paste the code back
New sandboxes Get the provider with --provider, no login Need a new login each
Token expiry and refresh You renew it (Claude's token lasts a year, bin/provider.sh --update) agy refreshes it itself, through oauth2.googleapis.com
Several agents, one account One provider for any number of sandboxes One login per sandbox, each revocable on its own
Depends on The agent accepting a token from the environment (or a header the proxy can fill in) Nothing beyond the agent's normal login

Why Antigravity CLI uses a login in the sandbox: it has no way to take a token from the environment or a file you hand it; it only uses its own login, stored in its own token storage. A provider would work only with workarounds: a fake Google metadata server in the sandbox that hands agy the placeholder (agy accepts this with AGY_ADC_AUTH=1, tested), and a gateway refresh that needs agy's OAuth client secret taken out of its binary plus your refresh token taken out of the macOS Keychain. That depends on undocumented internals that an update can break, so this repo doesn't do it. Gemini CLI, which does accept a token from the environment, is no option either: Google refuses Google-account logins from it ("This client is no longer supported for Gemini Code Assist for individuals") and points to Antigravity.

What that means in practice: treat an Antigravity sandbox as holding a live key to your Google account (with the cloud-platform scope). Don't widen its policy for other tasks; use a Claude Code or OpenCode sandbox for work that needs more network access, such as the browser or package registries.

Claude Code with a Claude subscription

Claude Code runs with a Claude subscription (Pro/Max) via an OAuth token, not an API key. The upstream claude-code.yaml profile only supports API keys, so this repo has its own profile: providers/claude-code-oauth.yaml. It injects the token as Authorization: Bearer only on requests to the endpoints listed in the profile (api.anthropic.com and platform.claude.com), so the real token never lives inside the sandbox.

Create an OAuth token (on the host)

Run on your own machine. It opens the browser to log in with your Claude account and prints a long-lived (1 year) token:

claude setup-token
  • Store the token in the Keychain (it prompts for the value), or see Credentials for .env and other secrets managers:
security add-generic-password -U -s openshell -a CLAUDE_CODE_OAUTH_TOKEN -w

Import the profile

(Skip this and the next section with bin/provider.sh claude, which imports the profile and creates the provider.)

openshell provider profile lint   -f providers/claude-code-oauth.yaml
openshell provider profile import -f providers/claude-code-oauth.yaml
  • After editing the file later, use update instead of import. See Update a profile.

Create the provider

The profile is only a template. The provider is the instance that holds your token in the gateway, and it is what a sandbox refers to with --provider. Importing the profile does not create the provider.

  • Check that the profile is imported; claude-code-oauth should be listed:
openshell provider profile list
  • Create the provider. --from-existing reads the token from the CLAUDE_CODE_OAUTH_TOKEN environment variable, so set it for this one command only (see Credentials):
    • --name is your own name for the provider, used later with --provider claude
    • --type is the id of the profile in providers/claude-code-oauth.yaml
(export CLAUDE_CODE_OAUTH_TOKEN="$(security find-generic-password -s openshell -a CLAUDE_CODE_OAUTH_TOKEN -w)"
 openshell provider create \
  --name claude \
  --type claude-code-oauth \
  --from-existing)

Expected output: ✓ Created provider claude

  • Verify; claude should be listed with type claude-code-oauth and 1 credential key:
openshell provider list
NAME        TYPE               CREDENTIAL_KEYS   CONFIG_KEYS
claude      claude-code-oauth  1                 0

Build the image

There is no ready-made image, so build one from images/claude-sandbox. It is node:22-slim with git, Claude Code and the ACP adapter claude-agent-acp (both installed via npm), plus two wrappers from the same folder that skip Claude Code's first-run onboarding: claude-start then starts claude, and claude-acp-start starts claude-agent-acp (for ACP).

podman build -t claude-sandbox:latest images/claude-sandbox

Or the same with make claude-sandbox.

Why the wrappers are needed: onboarding runs a connectivity check that connects to api.anthropic.com without going through the OpenShell proxy. The sandbox denies that connection, and Claude Code exits with Failed to connect to api.anthropic.com: EACCES. On first start, the wrappers copy /etc/claude-start.json, which holds {"hasCompletedOnboarding": true}, to ~/.claude.json (/sandbox/.claude.json), so the check is skipped. (The browser image replaces that file to also register its MCP server.) All other traffic goes through the proxy and works.

Create the sandbox

Quickest: bin/sandbox.sh claude [name] for Claude in your terminal, or add --vscode for VS Code. See Start a sandbox. The sections below show what it does by hand.

Always start Claude with claude-start, not claude.

With VS Code and a terminal (recommended)

The sandbox runs sleep infinity as its main process, so it keeps running while you start and quit Claude. The terminal policy lets VS Code open terminals inside it.

openshell sandbox create \
  --name claude-agent1 \
  --from claude-sandbox:latest \
  --provider claude \
  --policy policies/vscode-terminal.yaml \
  --detach \
  -- sleep infinity

openshell sandbox connect claude-agent1 --editor vscode

Then start Claude in one of these ways:

  • In VS Code's terminal (Terminal > New Terminal), which runs inside the sandbox:
cd /sandbox/myrepo
claude-start
  • From a terminal on your machine:
openshell sandbox exec claude-agent1 --tty --workdir /sandbox/myrepo -- claude-start
  • You can run several Claude sessions in the same sandbox, e.g. one per terminal tab.

Claude as the main process

Simpler, but the sandbox stops (Completed) when you quit Claude, and VS Code can no longer connect.

openshell sandbox create \
  --name claude-agent1 \
  --from claude-sandbox:latest \
  --provider claude \
  --policy policies/vscode-terminal.yaml \
  -- claude-start
  • Arguments are passed on to claude, e.g. -- claude-start --model sonnet
  • Smoke test (non-interactive): replace -- claude-start with -- claude-start -p 'reply with OK'

Things to watch for

  • Binary paths - only the binaries listed in the profile may reach the endpoints and get the token. The profile covers /usr/bin/claude, /usr/local/bin/claude and the npm install path /usr/local/lib/node_modules/@anthropic-ai/**. If requests are denied, check openshell logs claude-agent1 for the blocked binary path, add it to binaries and update the profile.
  • Don't use /login inside the sandbox - an interactive login would store the OAuth credentials in the sandbox (~/.claude/.credentials.json) and needs extra login hosts opened. setup-token + provider keeps the token outside.
  • Token expiry - the token is valid for a year. Regenerate with claude setup-token, store the new token (security add-generic-password -U ... replaces the old one), and update the provider:
bin/provider.sh --update claude

To be reminded before it expires, set the expiry on the provider, see Token expiry.

  • Only Anthropic hosts in the profile - OpenShell swaps the token placeholder for the real token on requests to every host in the profile. Shared third-party services such as sentry.io would let a manipulated agent send the token, or your code, to someone else's account, so the profile lists only api.anthropic.com and platform.claude.com. The image sets CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1, so Claude Code doesn't try to send telemetry, error reports or update checks (statsig.anthropic.com, sentry.io, Datadog).
  • The Claude Code VS Code extension would run its own bundled claude binary from ~/.vscode-server/extensions/..., which isn't in the profile's binaries list, so its requests will most likely be denied (not tested). Use the CLI in the terminal instead.

Import the profile

Things to watch for

  • Only the chat endpoint - the profile allows just POST /api/v1/chat/completions on openrouter.ai, the one call OpenCode makes. Other OpenRouter API paths (keys, credits, account) are denied. Check with openshell logs <sandbox> if a new OpenCode version needs more.
  • An agent can bring its own key - OpenShell only swaps its placeholder for your key; an Authorization header the agent sets itself goes through unchanged (tested: a made-up key reached OpenRouter and was rejected there). A manipulated agent could therefore send your code in a chat request on someone else's OpenRouter account, which can log prompts. The path rule above narrows this but can't close it. Keep secrets out of sandboxes, and treat what's in a sandbox as visible to the model provider anyway.
  • Binary path - only /usr/local/bin/opencode may use the key. If you install OpenCode elsewhere (e.g. via npm), add that path to the profile and update it.
  • Hosts left blocked - OpenCode tries models.opencode.ai (model list) and registry.npmjs.org (update check). Both are denied. OpenCode works without them, so leave them blocked unless you need them.
  • A more capable sandbox: agy-hyperframes - make agy-hyperframes, then bin/sandbox.sh agy-hyperframes. The image is built on claude-hyperframes and adds agy and the ACP adapter. npx hyperframes renders with headless Chromium and FFmpeg as there, and Playwright MCP is registered with agy (agy mcp add playwright playwright-mcp-start, done on first start by agy-init) so it can open and screenshot pages. Unlike the Claude image, nothing here blocks Playwright's browser_run_code_unsafe and browser_file_upload tools (that's Claude Code managed settings); the network rules are the limit. Pages other than the CDNs need a browser_sites-style rule in the policy. policies/agy-hyperframes.yaml is the agy policy plus the CDN, font and registry rules of the HyperFrames policy. That makes it the less safe choice: node and Chromium, which can read the tokens, may now reach those hosts (read-only, but a GET can carry data in its URL). Use it only for that work, log in, and run /logout and delete the sandbox afterwards. The HyperFrames skills are copied to ~/.claude/skills as in the Claude image, where agy doesn't look for them; npx hyperframes docs has the CLI's own docs. Log in once, as above; --acp works too.
  • npm packages: agy-node - make agy-node, then bin/sandbox.sh agy-node. The image is node:22-slim with agy and the ACP adapter, and policies/agy-node.yaml is the agy policy plus read-only access to registry.npmjs.org for /usr/local/bin/node (npm runs as node), so npm install works; the packages go in the workdir. It is less safe than a plain agy sandbox: node can read the tokens and reach the registry (a GET can carry data in its URL), and a package's install script runs with access to the tokens. Consider npm install --ignore-scripts, use it only for work that needs npm, and run /logout and delete the sandbox afterwards. Git and other registries (PyPI, GitHub) stay blocked. --acp works too.
  • Python packages: agy-python - make agy-python, then bin/sandbox.sh agy-python. The image is agy-sandbox plus Python 3 from Debian with pip and venv (Debian's pip refuses system-wide installs, so use python -m venv .venv && .venv/bin/pip install ... in the workdir). policies/agy-python.yaml is the agy policy plus read-only access to pypi.org and files.pythonhosted.org for /usr/bin/python3* (pip runs as Python). It is less safe than a plain agy sandbox for the same reasons as agy-node: Python can read the tokens and reach PyPI (a GET can carry data in its URL), and a package's setup script runs with access to the tokens. Use it only for work that needs pip, and run /logout and delete the sandbox afterwards. Other hosts (npm, GitHub) stay blocked. --acp works too.
  • The sandbox user is uid 1000 with HOME=/sandbox.

Antigravity CLI with a Google account

Antigravity CLI (agy) is Google's coding agent. It uses your Google account and its subscription (e.g. Google AI Pro/Ultra).

Unlike the other agents, there is no provider: you log in inside the sandbox, and agy keeps its OAuth tokens there. See Two ways to sign in for how that compares, and Things to watch for for what to do about it. Tested with a Google AI subscription: agy 1.3.3 in the sandbox signs in, shows the subscription's models and answers prompts.

Build the image

images/agy-sandbox is debian:bookworm-slim with git, ripgrep and agy at /usr/local/bin/agy, installed with Google's install script (which checks the download against the release manifest's SHA-512).

podman build -t agy-sandbox:latest images/agy-sandbox

Or the same with make agy-sandbox.

The policy

Without a provider, the network access comes from policies/antigravity.yaml: the terminal policy plus, for the agy binary only:

  • POST /token on oauth2.googleapis.com, to exchange the login code for tokens and to refresh the access token
  • GET /oauth2/v2/userinfo on www.googleapis.com and GET /a/** on lh3.googleusercontent.com, agy's eligibility check (your account's email, name and profile picture)
  • POST /v1internal:* and GET /v1internal/** on daily-cloudcode-pa.googleapis.com, the Code Assist API agy uses for everything else

Change it on a running sandbox with openshell policy set <sandbox> --policy policies/antigravity.yaml --wait.

Create the sandbox and log in

bin/sandbox.sh agy my-task

This creates the sandbox with the image and policy above (no --provider) and starts agy. By hand:

openshell sandbox create \
  --name agy-agent1 \
  --from agy-sandbox:latest \
  --policy policies/antigravity.yaml \
  --detach \
  -- sleep infinity

openshell sandbox exec agy-agent1 --tty --workdir /sandbox -- agy

On first start, agy prints a login URL (it can't open a browser in the sandbox):

  1. Open the URL in your browser on the Mac and sign in with your Google account.
  2. The browser ends up on antigravity.google with an authorization code. Copy it.
  3. Paste it into the "authorization code" field under the link in the terminal and press Enter. The login screen is about 26 lines high: in a smaller window the field is out of sight, so make the window taller or scroll down with Shift+↓.

The login stays in the sandbox (/sandbox), so you only do this once per sandbox. Non-interactive runs (bin/sandbox.sh agy my-task -- -p 'reply with OK') only work after that; before it, they stop with "authentication required".

Things to watch for

  • The tokens are in the sandbox - including the long-lived refresh token, readable by the agent and by anything else running there. The policy limits where they could be sent to the four Google hosts above. Every rule you add to such a sandbox (another site, a package registry, a browser) is another place they could go, so keep agy sandboxes to that policy. When you're done, run /logout in agy and delete the sandbox. To revoke the login entirely, remove Antigravity under Third-party access in your Google account.
  • Hosts left blocked - agy also tries play.googleapis.com (usage logs), antigravity-unleash.goog (feature flags) and www.gstatic.com. They are denied, and agy works without them. If a new version needs more, check openshell logs <sandbox> | grep DENIED (or bin/watch-denied.sh) and add it to the policy.
  • No self-update - agy normally updates itself; in the sandbox /usr is read-only and the update host isn't allowed, so it skips that. Get a newer version with make update, then create a new sandbox (and log in again).
  • ACP through a community adapter - agy has no Agent Client Protocol mode of its own. The image has google-antigravity-acp (pinned, MIT, small and not from Google), which drives agy's stream-json print mode and speaks ACP, so bin/sandbox.sh agy my-task --acp and bin/acp_client.py work once you have logged in. The adapter makes agy auto-approve tool permissions; set AGY_ACP_ASK=1 in the command to pass --no-skip-permissions. See ACP. Google may not like third-party tools driving agy with a subscription login, so use it knowingly.
  • The sandbox user is uid 1000 with HOME=/sandbox; agy keeps its settings and conversations in /sandbox/.gemini/antigravity-cli.

Working in sandboxes

The examples use claude-agent1. Everything works the same for the OpenCode and Antigravity CLI sandboxes.

Start and use a sandbox

Create a sandbox once, then use it as often as you like: with the agent in your terminal, with VS Code, or both. The sandbox runs sleep infinity as its main process, so it keeps running when you quit the agent or close VS Code, and the files stay.

You can do this by hand or with bin/sandbox.sh. The values per agent:

Agent Image Provider Agent command ACP command
Claude Code claude-sandbox:latest claude claude-start claude-acp-start
OpenCode opencode-sandbox:latest openrouter opencode -m openrouter/nvidia/nemotron-3.5-lightning:free opencode acp
Antigravity CLI agy-sandbox:latest none (policy antigravity.yaml) agy agy-acp-start (community adapter)

The variants (claude-browser, claude-hyperframes, agy-hyperframes, agy-node, agy-python) have the ACP command of the agent they are built on.

The examples below use Claude and the sandbox name my-task.

By hand

  1. Create the sandbox (once):
openshell sandbox create \
  --name my-task \
  --from claude-sandbox:latest \
  --provider claude \
  --policy policies/vscode-terminal.yaml \
  --detach \
  -- sleep infinity
  • --detach returns right away and leaves sleep infinity running in the background.
  • --policy adds terminal access, which VS Code's terminal needs (see Filesystem policy).
  • Wait until openshell sandbox list shows my-task as Ready.
  1. Use the agent in your terminal:
openshell sandbox exec my-task --workdir /sandbox -- claude-start
  • --workdir is the folder the agent starts in, e.g. /sandbox/myrepo.
  • Arguments after the agent command go to the agent, e.g. ... -- claude-start -p 'reply with OK' as a smoke test.
  • Quit the agent as usual. The sandbox keeps running.
  1. Or use VS Code:
openshell sandbox connect my-task --editor vscode
  • VS Code opens a window connected to the sandbox. Open a folder with File > Open Folder, and start the agent in Terminal > New Terminal with claude-start.
  • See VS Code for the one-time setup.
  1. Or open a shell in the sandbox to look around or run commands:
openshell sandbox exec my-task --workdir /sandbox -- bash
  • Leave the shell with exit or Ctrl-D. The sandbox keeps running.
  • The shell has the same restrictions as the agent, and the provider's credentials as placeholders, so you can start claude-start or opencode from it too.
  • A single command, no shell:
openshell sandbox exec my-task -- ls -la /sandbox
  • Plain SSH: after you've connected a sandbox once with --editor vscode, it has an SSH host entry (openshell-<name>.default), so this works:
ssh openshell-my-task.default

For other sandboxes, add the entry first:

openshell sandbox ssh-config my-task >> ~/.ssh/config

The entry tunnels SSH through the gateway with openshell ssh-proxy, so the sandbox doesn't need an open port. scp doesn't work over this connection and the images have no rsync. To copy files, use openshell sandbox upload and download (see Getting code in and out).

  1. Later: check that the sandbox is still running, and use it again with step 2, 3 or 4:
openshell sandbox list
  • Ready: running, use it.
  • Completed or Error: stopped. Delete it and create it again (step 1). Files in it are lost, so get your work out first (see Getting code in and out). NVIDIA's docs say openshell sandbox start runs the main command of such a sandbox again; on Podman with OpenShell 0.1.3 it printed an error here (already running generation) while the sandbox moved to Starting, so deleting and creating again is the safe route.
  1. When the task is done:
openshell sandbox delete my-task

VS Code

VS Code connects to a sandbox over SSH with the Remote-SSH extension. OpenShell tunnels the SSH connection through the gateway, so the sandbox doesn't expose any port.

One-time setup

  • Install the Remote-SSH extension, and make sure the code command works in a terminal (in VS Code: Shell Command: Install 'code' command in PATH).
  • Add this to your VS Code user settings (settings.json):
"remote.SSH.localServerDownload": "always",

VS Code installs "VS Code Server" in the sandbox on first connect. By default the sandbox downloads it itself, which fails because the sandbox can't reach Microsoft's servers. With this setting, your machine downloads it and copies it in over SSH.

Connect

The sandbox must be running (Ready in openshell sandbox list) and created with --policy policies/vscode-terminal.yaml, otherwise VS Code's terminal won't start.

openshell sandbox connect claude-agent1 --editor vscode
  • This opens a VS Code window connected to the sandbox. Use File > Open Folder to open e.g. /sandbox/myrepo.
  • The first connect takes up to a minute while VS Code Server is copied in. Later connects are quick.
  • The VS Code terminal runs inside the sandbox, with the same restrictions as the agent. It gets the provider's credentials as placeholders (openshell:...), so the agent works there.
  • You can also pass --editor vscode when you create a sandbox: openshell sandbox create --editor vscode ...
  • OpenShell adds Include "~/.config/openshell/ssh_config" to ~/.ssh/config, with one host per sandbox, e.g. openshell-claude-agent1.default. These hosts also show up in VS Code's Remote Explorer, and plain ssh openshell-claude-agent1.default works too.
  • Without --editor, openshell sandbox ssh-config claude-agent1 prints the host entry so you can add it yourself.

Things to watch for

  • Blocked hosts - VS Code Server tries to reach main.vscode-cdn.net and mobile.events.data.microsoft.com (telemetry). The logs show these as DENIED. Editing works without them, so leave them blocked.
  • Extensions in the sandbox - installing extensions on the remote side needs marketplace access, which is blocked. Add "remote.downloadExtensionsLocally": true to the settings, so VS Code downloads extensions on your machine and copies them in.
  • Don't approve rules for VS Code's node - the binary path contains the VS Code version (/sandbox/.vscode-server/cli/servers/Stable-<hash>/server/node), so an approved rule stops matching after a VS Code update.
  • Edits go into the sandbox - files you edit live in the sandbox, not on your machine. Get them out with git as described in Getting code in and out.

Getting code in and out

The examples use a repo at ./myrepo. The image needs git; both images from this repo have it.

There are three ways to do it, from safest to most convenient:

Approach Git credentials in sandbox Who pushes and opens the MR
1. Git bundles in and out (recommended) None You, from the host
2. Read-only clone in the sandbox, bundle out Read-only You, from the host
3. Push from inside the sandbox Write access, scoped to one repo The agent

Good to know about upload and download

  • openshell sandbox upload <sandbox> <local-path> <dest> puts a folder inside <dest>. Uploading ./myrepo to /sandbox/myrepo gives /sandbox/myrepo/myrepo, so upload to /sandbox instead.
  • upload follows .gitignore and leaves out the .git folder, so an uploaded repo has no history. Use a git bundle (below) to keep the history. --no-git-ignore uploads ignored files too.
  • openshell sandbox download <sandbox> <sandbox-path> <local-dest> copies files back to the host. The source has to be inside the sandbox's working directory.
  • --upload on sandbox create can't be combined with a command after --. Upload into a running sandbox instead.

Single files

For a file that isn't code in a repo (a spec, a data file, a screenshot or report the agent made), copy it with upload and download. Give a folder as the destination. The file lands in it under its own name. Into the sandbox, ./spec.md becomes /sandbox/spec.md:

openshell sandbox upload my-task ./spec.md /sandbox

Out of the sandbox, /sandbox/myrepo/report.html becomes ./report.html:

openshell sandbox download my-task /sandbox/myrepo/report.html .
  • Files git ignores aren't uploaded. Inside a git repo, upload applies .gitignore, so e.g. a .env or a build output is left out. A file outside any repo is uploaded as is (the CLI warns that it uploads "without Git filtering").
  • scp and rsync don't work over the sandbox's SSH connection (see Start and use a sandbox). Use upload and download.
  • Check what comes out before you open or run it. A file the agent wrote is untrusted, like its code.
  • Keep secrets out. Anything you upload is readable by the agent and can end up with the model provider.

1. Git bundles in and out (recommended)

A git bundle is a single file that contains commits, like a portable remote. The sandbox never gets git credentials or network access to your git host, and you review everything before it leaves your machine.

With the script

bin/bundle.sh does the steps below in two commands:

bin/bundle.sh in  <sandbox> <repo> [--branch NAME] [--base BRANCH]
bin/bundle.sh out <sandbox> <repo> [--branch NAME] [--base BRANCH] [--force]

A typical task, with the sandbox my-task and the repo ./myrepo. First bring the repo in:

bin/bundle.sh in my-task ./myrepo

The agent works in /sandbox/myrepo and commits on branch agent/my-task. Then bring its commits out, review them, push, and open the MR:

bin/bundle.sh out my-task ./myrepo
git -C ./myrepo diff main...agent/my-task
git -C ./myrepo push origin agent/my-task
  • in bundles only the base branch (main) and uploads it. Other branches and their history never reach the sandbox.
    • The first time, it creates /sandbox/<repo-name> and checks out the work branch from main. The branches from your machine are available as host/*, e.g. host/main, and the agent's git name and email are set.
    • Run it again to bring in newer commits from your machine. They arrive in host/* without touching the work branch; ask the agent to merge or rebase host/main if needed.
  • out bundles the work branch's commits that aren't in host/main, downloads them and fetches them into your repo as the same branch. It then shows the log and a diff summary.
    • Only commits are taken out. It warns if there are uncommitted changes in the sandbox.
    • The branch must not be checked out in your repo on the host.
    • If the agent rebased, the branch has diverged from the copy on your machine, and out stops. Run it with --force to overwrite your copy.
  • Options: --branch sets the work branch (default agent/<sandbox>) and --base the branch to start from and compare with (default main).

By hand

  • Pack the repo on the host and upload it:
git -C ./myrepo bundle create ../in.bundle --all
openshell sandbox upload claude-agent1 ./in.bundle /sandbox
  • Clone it inside the sandbox on a work branch, e.g. ask the agent to do it, or run:
openshell sandbox exec claude-agent1 -- sh -c '
  git clone -q /sandbox/in.bundle /sandbox/myrepo &&
  cd /sandbox/myrepo &&
  git config user.name "Claude (sandbox)" &&
  git config user.email "claude@sandbox.local" &&
  git checkout -b agent/my-task'
  • Let the agent work and commit on agent/my-task. Then pack the new commits and download them:
openshell sandbox exec claude-agent1 -- \
  git -C /sandbox/myrepo bundle create /sandbox/out.bundle main..agent/my-task
openshell sandbox download claude-agent1 /sandbox/out.bundle .
  • Fetch the branch into your repo, review it, then push and open the MR yourself:
git -C ./myrepo fetch ../out.bundle agent/my-task:agent/my-task
git -C ./myrepo log --oneline main..agent/my-task
git -C ./myrepo diff main agent/my-task
git -C ./myrepo push origin agent/my-task
  • To give the sandbox newer commits from main, create a new in.bundle, upload it again, and run git fetch /sandbox/in.bundle main:main inside the sandbox.

2. Read-only clone in the sandbox

Attach a git provider that only allows reads, so the agent can clone and fetch by itself. Get the results out with a bundle as in approach 1. The upstream github.yaml profile works this way: it allows clone and fetch, but not push.

openshell provider profile import --url https://raw.githubusercontent.com/NVIDIA/OpenShell/main/providers/github.yaml
GITHUB_TOKEN=<read-only-token> openshell provider create --name github-ro --type github --from-existing
openshell sandbox create ... --provider claude --provider github-ro ...
  • There is no upstream GitLab profile. For GitLab, write your own for your GitLab host (see Provider profiles).

3. Push from inside the sandbox

Possible, but a sandbox that can push can also send your code anywhere the token reaches. Only do this when you trust the setup, and limit it:

  • Use a token limited to one repository (e.g. a GitHub fine-grained token or a GitLab project access token).
  • Allow pushes (git-receive-pack) for that one repository only, with a policy applied by openshell policy set. The official GitHub Push Access tutorial shows the exact policy.
  • Protect main on the git server. The policy can limit which repository, but not which branch.
  • Opening the MR or PR from inside also needs gh or glab in the image, and API access to that repository in the policy.

Viewing a web page from the sandbox

To see and click through a page the agent builds, the agent serves it on a port in the sandbox, and OpenShell forwards that port to your machine. The forward goes through the gateway (over SSH, like VS Code), so the sandbox opens no port and no network rule is needed.

  1. Ask the agent to serve the page on a port, in the background, e.g. "serve the page on port 3000". A small server in Node.js (which the Claude image has; it has no Python) needs nothing else. A dev server like npx vite must first be installed from npm, which needs the npm_registry rule from policies/example.yaml. Binding to 127.0.0.1 in the sandbox is enough.
  2. Forward the port on your machine:
openshell forward start 3000 my-task -d
✓ Forwarding port 3000 to sandbox my-task in the background
  Access at: http://127.0.0.1:3000/
  Stop with: openshell forward stop 3000 my-task
  1. Open http://127.0.0.1:3000. With a dev server that reloads on changes, you see the agent's edits right away.
  2. List and stop forwards:
openshell forward list
openshell forward stop 3000 my-task
  • Without -d the forward runs in the foreground until Ctrl-C.
  • Bound to 127.0.0.1 on your machine by default, so others on your network can't reach it. openshell forward start 0.0.0.0:3000 ... would open it to them; don't.
  • One forward per local port. A second forward start on the same port fails with Port 3000 is already forwarded. Stop the old one first, or use another port.
  • The page runs outside the sandbox. In your browser, the agent's code has your network access, not the sandbox's: it can call other services on your localhost (e.g. an MCP server on the host), send data to any site, and use whatever your browser is logged into. Open it in a private window or a separate browser profile without logins, and treat it like the agent's other code until you've reviewed it.
  • Alternatives: VS Code forwards ports itself when connected with --editor vscode (see its Ports tab). For one static page, download it and open the file. openshell service expose publishes a service through the gateway under its own URL, which is more than viewing it yourself needs.
  • For the agent itself to look at the page, use the browser in the sandbox instead. It reaches localhost there without any forward.

Many sandboxes in parallel

  • One sandbox per task or branch, named after the task (claude-auth-fix, claude-docs). Each has its own filesystem, policy and approved rules, so agents don't interfere with each other.
  • Providers are shared - create a provider once and attach it to every sandbox with --provider.
  • Labels - add e.g. --label project=foo --label task=auth on create, then list with openshell sandbox list --selector project=foo.
  • Templates - store the image and resources once, then create sandboxes from it. --template can't be combined with --from, --cpu, --memory, --gpu, --env or --driver-config-json; those belong on the template (template create also takes --gpu, --label and --env). template list, get and delete manage them:
openshell sandbox template create claude --image claude-sandbox:latest --cpu 2 --memory 4Gi
openshell sandbox create --name claude-auth-fix --template claude --provider claude \
  --policy policies/vscode-terminal.yaml --detach -- sleep infinity
  • Resources - all sandboxes run inside the one Podman machine. Give it room if you run several:
podman machine stop
podman machine set --cpus 6 --memory 12288
podman machine start
  • Usage limits - parallel Claude sessions share your Claude subscription's limits.
  • Approved rules are per sandbox and reset when the sandbox is recreated. Hosts every sandbox needs belong in the profile or in a policy file.
  • Overview and cleanup - openshell sandbox list, and openshell sandbox delete <sandbox> when a task is done.

Optional additions to the basic setup. Each one gives the agent more reach, so add it when a task needs it.

MCP servers in containers on the host

A sandbox can't run containers, so a stdio MCP server that ships as a container image runs on the host, and the agent uses it over HTTP. OpenShell then sees every request and can filter tools. Over stdio inside the sandbox it can't. The server's secrets also stay in its container.

  1. Run it with an HTTP transport. Use the server's own HTTP mode if it has one, or put a stdio-to-HTTP bridge such as supergateway in front of it. Bind the port to 127.0.0.1 so only your machine can reach it:
podman run -d --name my-mcp -p 127.0.0.1:8000:8000 my-mcp-image \
  npx -y supergateway --stdio "my-mcp-server" --outputTransport streamableHttp --port 8000

With an image that only contains the server, build a small image with Node.js and supergateway on top of it. 2. Find the host's IP in the sandbox (192.168.127.254 with Podman on macOS):

openshell sandbox exec my-task -- getent hosts host.containers.internal
  1. Add a rule with that IP as host and the tools you allow, then load it with openshell policy set (see Sandbox policies):
  host_mcp:
    name: host-mcp
    endpoints:
      - host: 192.168.127.254
        port: 8000
        path: /mcp
        protocol: mcp
        enforcement: enforce
        mcp:
          versions: ["2025-03-26", "2025-06-18", "2025-11-25"]
          allow_all_known_mcp_methods: true
        rules:
          - allow:
              tool: echo           # or e.g. "read_*"; every other tool is denied
    binaries:
      - path: /usr/local/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe
  1. Add the server to the agent by IP: claude mcp add --transport http my-mcp http://192.168.127.254:8000/mcp.
  • Use the IP, not host.containers.internal. The name comes from /etc/hosts in the sandbox, so a rule with that name never matches (EACCES). A URL with the name gets 403 request_authority_mismatch, because the Host header must match the rule.
  • The server runs outside the sandbox. Its own actions are only limited by its container, so give it only the mounts and tokens it needs.
  • Test: tests/host-mcp/run.sh runs a test server this way and checks that an allowed tool works and another is denied. --claude also checks it with Claude Code.

ACP (Agent Client Protocol)

To build a UI that runs on the host and talks to the agent in the sandbox, use ACP. ACP is JSON-RPC over the agent's stdin and stdout, so no port is opened in the sandbox: the client starts the agent through the gateway and speaks ACP over the pipes, like the SSH tunnel for VS Code.

bin/sandbox.sh opencode my-task --acp
bin/sandbox.sh claude my-task --acp
bin/sandbox.sh agy my-task --acp

These run the following, respectively (for OpenCode, plus the model in OPENCODE_CONFIG_CONTENT, see below):

openshell sandbox exec my-task --no-tty --no-login-shell --workdir /sandbox -- opencode acp
openshell sandbox exec my-task --no-tty --no-login-shell --workdir /sandbox -- claude-acp-start
  • Client side: spawn the command above as a subprocess and give its stdin/stdout to an ACP client library (e.g. @agentclientprotocol/sdk for TypeScript). Flow: initialize, session/new (with cwd as a path inside the sandbox), then session/prompt. Keep the process running for the whole session. The agent's stderr is log output; show it separately.
  • Clean stdout: --no-tty stops a pty from mangling the stream, --no-login-shell stops profile scripts from printing before the first message. The script prints its own messages (e.g. "Creating sandbox...") to stderr, so create the sandbox once beforehand if your client is strict.
  • Keep the sandbox's isolation: in initialize, don't advertise the fs and terminal client capabilities. Otherwise the agent may ask your UI to read, write and run commands on the host. Without them it uses its own tools inside the sandbox. Handle session/request_permission in the UI to approve tool use.
  • OpenCode: opencode acp is built in, so the image needs no changes. It has no -m flag, so the script sets the model (OPENCODE_MODEL, same default as above) through the OPENCODE_CONFIG_CONTENT env var. Without a model, OpenCode picks an opencode/... one and fails with "Cannot connect to API", because opencode.ai is blocked.
  • Claude Code: has no native ACP mode, so the image includes the adapter @agentclientprotocol/claude-agent-acp. --acp runs claude-acp-start, which skips onboarding (like claude-start) and starts claude-agent-acp. The adapter runs Claude Code through the Claude Agent SDK, which by default uses its own bundled claude binary deep in the adapter's node_modules. That path is not in the profile's binaries, so its requests would go out without the token. The image sets CLAUDE_CODE_EXECUTABLE to the globally installed claude.exe instead, which the profile already allows. Rebuild the image and create a new sandbox after updating; existing sandboxes keep the old image.
  • Antigravity CLI: agy has no ACP mode, so the image includes the community adapter google-antigravity-acp (Node.js, pinned in the Dockerfile). --acp runs agy-acp-start, which starts it with /usr/local/bin/agy, the binary the policy lets reach Google. Log in once first (bin/sandbox.sh agy my-task); without a login the session fails with "agy process exited before emitting init event". The adapter has no loadSession, and auto-approves tool permissions unless AGY_ACP_ASK=1.
  • All images: every image has its agent's ACP command, because the variants are built on the base images: claude-browser and claude-hyperframes have claude-acp-start, and agy-hyperframes, agy-node and agy-python have agy-acp-start (agy-hyperframes and claude-hyperframes run hyperframes-init first; agy-hyperframes also registers Playwright MCP). --acp works with every profile (browser, hyperframes, kirocrew, agy-node, agy-python, and so on). agy-hyperframes also contains Claude's command, so acp_client.py takes it for agy.
  • Network: egress rules are unchanged; ACP doesn't open anything.
  • Fallback: if the gRPC exec stream misbehaves, use the SSH route (see By hand): ssh openshell-my-task.default opencode acp or ... claude-acp-start (add -T to disable the pty).
  • Example client: bin/acp_client.py is a minimal client (Python 3, no dependencies) that lists sandboxes and chats with the agent in one:
bin/acp_client.py list
bin/acp_client.py connect <sandbox> [--agent opencode|claude|agy] [--model M] [--cwd /sandbox]

Type a prompt and press Enter; /help lists the commands, /models [FILTER] lists the models the agent offers, /model ID switches model for the session, /commands lists the agent's own slash commands (e.g. /init, /review), /quit or Ctrl-D exits, and Ctrl-C cancels a running prompt. It checks that the sandbox exists and is Ready, prints the agent's text and tool calls, asks permission requests on the terminal, and refuses any fs/* or terminal/* request from the agent. If the agent fails or exits, it shows the agent's last output with a hint (missing adapter, blocked API host, wrong model). Options: --timeout SEC for startup, -v for the JSON-RPC traffic and the agent's stderr. Exit codes: 0 ok, 1 agent error, 2 bad usage or sandbox. Without --agent, it picks the agent by which ACP command the sandbox has (claude-acp-start, agy-acp-start or opencode). Use it as a starting point for your UI.

  • Test it before building the UI: printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":1,"clientCapabilities":{}}}' | bin/sandbox.sh opencode my-task --acp (or claude instead of opencode) should print one JSON response.

Claude Code as an ACP backend for an external Kiro Crew

This is the other direction from Kiro Crew with Claude Code over ACP: there, Kiro Crew's gateway runs inside the sandbox and drives Claude Code there too. Here, an existing Kiro Crew install stays outside any sandbox — on this same Mac — and uses a sandbox purely as Claude Code's execution environment. No Kiro Crew runs inside that sandbox.

Kiro Crew's agent.acp_backend = claude setting spawns one local executable, named by the CLAUDE_AGENT_ACP_BIN environment variable on the gateway process, and runs it directly — not through a shell, so it can't be a command line with arguments, only a single file. bin/kirocrew-acp-backend.sh is that file: it execs bin/sandbox.sh <profile> <name> --acp, the same thing VS Code or bin/acp_client.py use, which prints nothing but the ACP protocol to stdout (see ACP).

export CLAUDE_AGENT_ACP_BIN=/path/to/openshell-configs/bin/kirocrew-acp-backend.sh
export KIROCREW_ACP_SANDBOX=my-backend     # optional, defaults to kirocrew-claude; OpenShell sandbox names are max 19 characters
export KIROCREW_ACP_PROFILE=hyperframes    # optional, a different profile (loses the cwd auto-create below)
kirocrew config set agent.acp_backend claude
kirocrew restart

Set the two KIROCREW_ACP_* variables (or leave them at their defaults) in the same environment the CLAUDE_AGENT_ACP_BIN export lands in — a shell profile, or wherever Kiro Crew's launchd/systemd service reads its environment from — since the wrapper reads them at spawn time, once per session. The sandbox is created on first use and reused after that, exactly as bin/sandbox.sh always does; delete it with openshell sandbox delete <name> to start over. Claude's provider token still comes from the sandbox's attached claude provider, unchanged from any other use.

Create the sandbox once before the first chat. Kiro Crew's ACP spawn expects a near-instant local process start. The first time this wrapper runs for a name OpenShell has no sandbox for, it has to create one and poll until it's Ready (up to 3 minutes), which reads as ⟳ Connection lost — retrying… to a session that gave up waiting. Avoid it by running the wrapper's underlying command yourself first, so the sandbox already exists and is Ready by the time Kiro Crew's first session reaches it:

bin/sandbox.sh claude kirocrew-claude -- -p 'reply with OK'

(swap claude and kirocrew-claude for your KIROCREW_ACP_PROFILE/KIROCREW_ACP_SANDBOX, if set).

The working directory Kiro Crew asks for doesn't exist in the sandbox, and can't be created there from inside it. Kiro Crew assumes its ACP backend shares its own filesystem, the way a literal local subprocess would, and sends session/new's cwd as a path on its own machine (e.g. /Users/you/dev/kirocrew/<workspace>). claude-agent-acp validates that path on the machine actually running the agent — the sandbox — and refuses it there with Invalid params: cwd does not exist on the machine running the agent. The sandbox can't simply create it either: /Users/... doesn't exist in the sandbox's filesystem, and creating it needs write access to /, which Landlock must never grant (that's the sandbox's actual boundary, not an oversight).

Fixing it needs two parts, both already wired into profiles/kirocrew-backend.env, the default KIROCREW_ACP_PROFILE:

  • images/claude-kirocrew-backend, built on claude-sandbox, bakes a symlink for your Mac's Kiro Crew workspace root into the sandbox's own writable home (<your root> -> /sandbox/kirocrew-workspace) at build time, as root, with no Landlock involved — the only place that path can be created at all. Build it with your own workspace root as a build arg (find yours from the cwd Kiro Crew's error names, or kirocrew config get agent.workspace_dir):
make claude-kirocrew-backend KIROCREW_WORKSPACE_ROOT=/Users/you/dev/kirocrew
  • policies/kirocrew-backend.yaml adds read-only access to /Users so the symlink is visible at all — Landlock denies even reading an unlisted path. No write access to /Users is needed: once the kernel follows the symlink, writes land under /sandbox, already read-write via include_workdir.
  • acp_cmd=claude-acp-mkcwd-start (a profile field like agent, image, policy and cmd, overriding the agent's own ACP command) runs the real adapter behind claude-acp-mkcwd.js, a transparent line-by-line proxy (ACP over stdio is newline-delimited JSON) that creates any cwd it sees in a request before forwarding the message unchanged. It walks the path itself rather than using a plain recursive mkdir, because fs.mkdirSync(cwd, {recursive: true}) treats an existing symlink as proof its target is already there and never creates what the symlink actually points to — the exact case the baked-in symlink is. A path the sandbox's filesystem policy would refuse anyway still fails exactly as before; this only pre-creates directories the sandbox could already write to, following a symlink chain the image controls.

Switching KIROCREW_ACP_PROFILE away from kirocrew-backend loses all of this and brings the original error back.

agent.acp_backend and CLAUDE_AGENT_ACP_BIN are both read once at startup (the adapter path is cached after its first resolution), so a change needs kirocrew restart, and agent.acp_backend is one setting for the whole gateway — every session uses the same sandbox.

Kiro Crew's own built-in tools (kirocrew-core, kirocrew-cron) fail with ENOENT ... posix_spawn. They can't be fixed; see Choosing which MCP servers an agent can reach, case by case below for why, and for the general mechanism that does work for any other MCP server.

Choosing which MCP servers an agent can reach, case by case

"Reach" means something different depending on what kind of MCP server it is, so there are two separate controls, not one.

A remote MCP server (HTTP) is one the agent dials out to itself — Claude Code connects to it directly, the same as any other outbound connection. This is governed by a protocol: mcp network policy rule: OpenShell reads every MCP request at L7 and checks the method and, for tools/call, the tool name, down to individual tools. policies/example.yaml's context7_mcp and huggingface_mcp blocks are the full worked syntax, explained in Example policy with network rules; policies/kirocrew-backend.yaml has a ready-to-fill-in, commented-out copy of the same shape. The short version:

network_policies:
  some_mcp_server:
    name: some-mcp-server
    endpoints:
      - host: mcp.example.com
        port: 443
        path: /mcp
        protocol: mcp
        enforcement: enforce
        mcp:
          versions: ["2025-03-26", "2025-06-18", "2025-11-25"]
        rules:
          - allow:
              method: initialize
          - allow:
              method: notifications/initialized
          - allow:
              method: tools/list
          - allow:
              method: tools/call
              tool:
                any: [tool_one, tool_two]   # only these tools, by name
    binaries:
      - path: /usr/local/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe

Add it per profile's policy file, one block per server, and add the server in Claude Code as usual (claude mcp add --transport http <name> https://mcp.example.com/mcp). binaries: is the per-agent scoping — Claude's own binary dials remote MCP servers itself, so that's the entry for any Claude profile.

A local MCP server (stdio) is spawned as a child process inside the sandbox — there's no network connection to filter, since it's a pipe, not a socket. Its "reach" is simply whether its binary exists in the image at all: leave it out of a profile's image and it can never be spawned, no policy needed. If that local process then makes its own outbound network calls, that call is governed exactly like case one — a binaries: entry scoped to its specific path, in whichever profile's policy it runs under.

Where this hits a hard wall: kirocrew-core and kirocrew-cron (the two built-in MCP servers Claude Code as an ACP backend for an external Kiro Crew runs into as ENOENT ... posix_spawn) are local MCP servers whose command is a macOS app binary that doesn't exist in the Linux sandbox at all — not fixable by any policy, since the binary itself is the problem, not what it's allowed to reach. Worse, even installing an equivalent Linux binary wouldn't help: kiro_crew's mcp_core.py and mcp_cron.py dial http://127.0.0.1:<port> — the gateway's own loopback — and check a local-secret file for same-machine ownership, the identical check that blocks Remote Crew over SSH. Inside the sandbox, 127.0.0.1 is the sandbox's own loopback; nothing is listening there, and the local-secret check would refuse a non-local caller regardless. Disabling them for a sandboxed session (dropping @kirocrew-cron/@kirocrew-core from the agent spec Kiro Crew uses) is the only real fix, not a network rule.

Headless browser use

Claude Code can use a headless Chromium that runs inside the sandbox, through Playwright MCP. Because the browser runs in the sandbox, OpenShell's network rules decide which sites it may reach, the same way as for any other program. The browser starts with an empty profile in memory, so it has none of your cookies or logins.

Why in the sandbox

  • The risk is data going out, not only bad pages coming in. Every page load can carry data in its URL (https://evil.example/?d=<your code>). A page the agent reads can tell it to do exactly that (prompt injection), and allowing only GET requests doesn't stop it. The one control that works is the list of hosts the browser may reach.
  • Not your own Chrome (Claude in Chrome, or the agent attached to your Chrome over CDP). The agent would act with all your logins, outside the sandbox.
  • Not Playwright MCP on the host, like the MCP servers on the host. A protocol: mcp rule can filter tool names, but it doesn't check arguments, so it can't check URLs. The browser's own traffic would also bypass OpenShell. Playwright's --allowed-origins option is documented as not a security boundary.

Set it up

  1. Build the image on top of claude-sandbox (build that one first, see Build the image):
podman build -t claude-browser:latest images/claude-browser

Or make claude-browser, which builds both. 2. List the sites the browser may open under browser_sites in policies/browser.yaml. It allows only example.com as a placeholder:

  browser_sites:
    name: browser-sites
    endpoints:
      - host: docs.python.org      # the sites for your task
        port: 443
    binaries:
      - path: /opt/ms-playwright/**   # only Chromium gets this rule
  1. Create the sandbox with the script, or by hand:
bin/sandbox.sh browser

openshell sandbox create --name web-task --from claude-browser:latest --provider claude \
  --policy policies/browser.yaml --detach -- sleep infinity
openshell sandbox exec web-task --workdir /sandbox -- claude-start
  1. Ask Claude to use the browser, e.g. "open http://localhost:3000 and check the login form". /mcp in Claude shows the playwright server.

What the image adds

images/claude-browser builds on claude-sandbox. Its Dockerfile copies in the files from that folder:

  • Playwright MCP and headless Chromium in /opt/ms-playwright. The path is fixed and read-only in the sandbox, so the rule can name the Chromium binary (/opt/ms-playwright/**) and the agent can't replace it.
  • The playwright MCP server in Claude Code. claude-start copies /etc/claude-start.json to ~/.claude.json on first start. The base image's file only skips onboarding; this image's file also registers the server.
  • playwright-mcp-start starts the server. OpenShell decrypts HTTPS with a CA it creates for each sandbox. Programs trust it through SSL_CERT_FILE and similar variables, but Chromium only trusts its own NSS database. Without it, every HTTPS page fails with ERR_CERT_AUTHORITY_INVALID, so the script adds the CA there on every start.
  • /etc/playwright-mcp.json: headless, profile in memory only, Chromium's own sandbox off, and --no-zygote. OpenShell's syscall filter makes Chromium's zygote process crash (Target crashed) even with its sandbox off. The OpenShell sandbox is the boundary.
  • Denied tools, in managed settings (/etc/claude-code/managed-settings.json, which the agent can't change): browser_run_code_unsafe (runs any code in the MCP server) and browser_file_upload (sends local files to a site). Claude Code then doesn't offer these tools at all. This is extra caution, not the boundary: the agent can run code with Bash anyway, and the network rules limit where anything can go.

Allowing sites

  • Pages on the sandbox itself (a dev server on localhost or 127.0.0.1) work without a rule. This is the safest use: testing what the agent builds needs no outside access.
  • Any other site must be in browser_sites, or it fails with net::ERR_NETWORK_ACCESS_DENIED. Change the list on a running sandbox with openshell policy set web-task --policy policies/browser.yaml --wait, or approve the proposed rules for the Chromium binary (see Network rules).
  • What a page loads from other hosts (CDNs, fonts, APIs) is denied too. The page may still be usable. If not, check openshell logs web-task | grep DENIED and add the hosts it needs.
  • List only sites you trust with what the agent can see. Each allowed site can receive data. Big sites with user content (GitHub, pastebins, any site where people post) are where a manipulated agent could send it.
  • Chromium tries www.google.com and update.googleapis.com at start. Those show up as DENIED in the logs. That's harmless, so leave them blocked.

Things to watch for

  • Claude Code only. The OpenCode image is Alpine-based, and Playwright's Chromium doesn't run on Alpine.
  • The agent can change its own MCP config in ~/.claude.json, e.g. remove the in-memory profile. That doesn't weaken the network and filesystem limits, which OpenShell enforces outside the agent.
  • Page content is untrusted input for the agent, like files it downloads. Keep secrets out of browser sandboxes.
  • Size and memory: the image is about 1.9 GB, and Chromium needs memory. Give the Podman machine more if you run several (see Many sandboxes in parallel).
  • Existing sandboxes keep their old image. Create a new one after rebuilding.
  • Test: tests/browser/run.sh creates a sandbox and checks that an allowed site loads, a site not in the list is denied, and a local server on 127.0.0.1 and localhost loads. --claude also checks it with Claude Code.

HyperFrames

HyperFrames makes videos from HTML: the agent writes a composition (HTML, CSS and GSAP), HyperFrames previews it in a web studio and renders it to MP4 with headless Chrome and FFmpeg. The claude-hyperframes image has all of it, plus the HyperFrames skills for Claude Code. You watch and edit in the HyperFrames Studio from your own browser, through a forwarded port.

Set it up

  1. Build the image. It builds on claude-browser, which builds on claude-sandbox; make builds all three in order:
make claude-hyperframes

Or by hand:

podman build -t claude-sandbox:latest     images/claude-sandbox
podman build -t claude-browser:latest     images/claude-browser
podman build -t claude-hyperframes:latest images/claude-hyperframes
  1. Create the sandbox and forward the preview port. The hyperframes profile (profiles/hyperframes.env) uses the image and policies/hyperframes.yaml and starts the port forward for 3102 in the background:
bin/sandbox.sh hyperframes
  1. Ask Claude for a video, and to serve the preview on that port, e.g. "Make a 10-second launch video for our CLI in /sandbox/launch. When it passes hyperframes check, start the preview with npx hyperframes preview --background --no-open --port 3102."
  2. Open http://127.0.0.1:3102 on your machine. This is HyperFrames Studio: play, scrub, edit, and see the agent's changes as it works.
  3. Get the video out when it's rendered (npx hyperframes render, by default to renders/ in the project):
openshell sandbox download my-video /sandbox/launch/renders/launch.mp4 .

By hand, without the script:

openshell sandbox create --name my-video --from claude-hyperframes:latest --provider claude \
  --policy policies/hyperframes.yaml --detach -- sleep infinity
openshell forward start 3102 my-video -d
openshell sandbox exec my-video --workdir /sandbox -- claude-start

What the image adds

images/claude-hyperframes builds on claude-browser (Playwright MCP and headless Chromium, see What the image adds above), so Claude can also open the preview itself and take screenshots. On top of that:

  • The HyperFrames CLI (npm hyperframes, pinned with ARG HYPERFRAMES_VERSION), FFmpeg, and fonts (Liberation, Noto including CJK and emoji) for rendering.
  • The HyperFrames skills of the same release (hyperframes, hyperframes-core, hyperframes-cli, general-video, media-use and the rest), copied to ~/.claude/skills on first start. They aren't installed as a plugin, so Claude doesn't try to update them from GitHub.
  • Rendering with Playwright's headless Chromium (HYPERFRAMES_BROWSER_PATH). HyperFrames normally downloads its own Chrome, which the sandbox can't.
  • hyperframes-init, run by claude-start and claude-acp-start: copies the skills, and adds the OpenShell CA to Chromium's certificate store. Without the CA, every CDN load in a render or check fails with ERR_CERT_AUTHORITY_INVALID, GSAP never loads, and videos come out still.
  • A patch for one HyperFrames call. The render worker lowers its own process priority, which OpenShell's syscall filter doesn't allow, so every render failed with uv_os_setpriority returned EPERM. The image makes that call best-effort. If a new HyperFrames version changes that code, the build fails at that step, so the patch gets checked.
  • Quiet by default: no telemetry (HYPERFRAMES_NO_TELEMETRY, DO_NOT_TRACK), no update checks, no skill downloads on init (HYPERFRAMES_SKIP_SKILLS).

The policy

policies/hyperframes.yaml has the browser policy's filesystem rules and allows, read-only (GET):

  • For Chromium: cdn.jsdelivr.net, unpkg.com, cdnjs.cloudflare.com, fonts.googleapis.com, fonts.gstatic.com. Compositions load GSAP and other libraries and fonts from these.
  • For the CLI (node): the same font and jsDelivr hosts, hyperframes.heygen.com (docs and schemas), and raw.githubusercontent.com, but only paths under /heygen-com/hyperframes/ (the block registry for hyperframes add and catalog).

The preview on 127.0.0.1 in the sandbox needs no rule. A composition that loads something else (an image from a website, another CDN) shows it as DENIED in openshell logs my-video. Add the host and apply it to the running sandbox with openshell policy set my-video --policy policies/hyperframes.yaml --wait.

With Antigravity CLI

bin/sandbox.sh agy-hyperframes does the same with agy instead of Claude Code, using the agy-hyperframes image (built on claude-hyperframes, plus agy and the ACP adapter) and policies/agy-hyperframes.yaml. Playwright MCP is registered with agy on first start, so it can use the headless browser. The skills are still copied to ~/.claude/skills, where agy doesn't look for them. Because agy's login tokens sit in the sandbox, read the warning in agents.md first.

Things to watch for

  • Port in use on your machine: openshell forward uses the same port number on both sides, and --forward fails if the port is taken (lsof -i :3102). HyperFrames' default preview port 3002 is often in use if you also run HyperFrames on the host, so pick another, as above.
  • The Studio runs the agent's code in your browser, outside the sandbox. See Viewing a web page from the sandbox. Use a private window.
  • hyperframes catalog stalls in the sandbox. It fetches hundreds of registry files from raw.githubusercontent.com. OpenShell maps each allowed host to a short-lived internal address, and Node keeps reusing connections after that mapping expires, so they're denied (transparent TCP mapping is expired in openshell logs) and the command hangs. While it runs, other HyperFrames commands in the sandbox may hang too, so stop it. hyperframes add <name> works, so browse the catalog at hyperframes.heygen.com and tell the agent which block to add.
  • Not included: local transcription (whisper.cpp), local voice (Kokoro) and music (MusicGen) models, and HeyGen's cloud features (avatars, TTS, cloud rendering), which need a HeyGen API key and api.heygen.com. npx hyperframes doctor lists what's missing; Docker, /dev/shm size and these optional models show as failed and don't matter for rendering.
  • Rendering uses software GL, so it's slower than on a Mac with a GPU: about 1.5 s of render time per second of video for a simple composition.
  • npx contacts registry.npmjs.org once, which shows as DENIED. HyperFrames is installed globally, so it works anyway.
  • Size: the image adds about 0.5 GB to claude-browser (2.3 GB in all).
  • Test: tests/hyperframes/run.sh creates a sandbox, renders a project, checks that hyperframes check loads GSAP without errors, and that the preview is reachable from your machine through a forwarded port. --claude also has Claude Code make and render a short video.

  • The skill clean-vector-from-raster (images/claude-graphics/skills): a workflow for turning a raster illustration (e.g. one figure from a sprite sheet on a chroma-key background) into a clean, print-ready SVG: prepare the image in PhotoCraft (crop, upscale, smooth), trace it in VectorCraft, simplify and export. To add a skill, put its folder in images/claude-graphics/skills/ and rebuild.

The default background is magenta, as spill: min(r, b) - g >= 30 and min(r, b) >= 110, which catches #ff00ff, lighter magentas such as #fc3efb and the blended edges, and leaves dark hair and outlines. The gallery

graphics-gallery [--dir /sandbox] [--port 3102] [--host 127.0.0.1] [--background] serves a page with a grid of thumbnails of the images below --dir (PNG, JPEG, GIF, WebP, SVG, AVIF, BMP, TIFF), newest first. It checks for new files every three seconds, so images appear as Claude writes them. You can filter by name and folder, sort by date, name or size, and click an image for a large view (arrow keys move between images, Esc closes) or to open the original.

  • It starts by itself. claude-start and claude-acp-start (through graphics-init) run graphics-gallery --background, which detaches, logs to /tmp/graphics-gallery.log and does nothing if the port is already in use, so it keeps running after the agent quits and a second start doesn't make a second server. It starts when the agent starts, not when the sandbox is created, so with --vscode or a plain sandbox exec start it yourself (graphics-gallery --background). To use another port or folder, run graphics-gallery --port N --dir D yourself.
  • Opening it: you reach it through a port forward, which bin/sandbox.sh graphics starts for 3102 every time you run it (or openshell forward start 3102 graphics -d by hand). The forward goes through the gateway, so the sandbox opens no port and needs no network rule. Then open http://127.0.0.1:3102. Ask Claude to put its results in /sandbox, in folders if you like; the folder menu follows them.
  • Read-only: GET only, and only image files below --dir.   • PDFs and PSDs aren't shown, because browsers don't render them as images. Ask Claude to export PNG or SVG next to them.
  • Source: images/claude-graphics/graphics-gallery, one Python file; change it and rebuild the image to customize the page.

Installing Python packages

The policy lets python3 and uv reach PyPI, so the agent can install packages. Nothing can make an installed package safe; the image and these habits limit what a bad one can do.

Wheels and source distributions. PyPI holds two kinds of files. A wheel (.whl) is prebuilt: installing it only unpacks files, and no package code runs. A source distribution (.tar.gz) has to be built first, which runs the package's own build code (setup.py or a build backend) at install time, with the agent's rights, before you have used the package. Popular packages publish wheels; others only have the source file.

The image installs wheels only. PIP_ONLY_BINARY=:all: is set for pip, and uv.toml in /etc/uv/uv.toml sets no-build = true for uv, for uv pip, uv add, uv sync and uvx. (uv's UV_NO_BUILD variable would not do it: uv pip ignores it, so the image uses the config file.) A package with only a source file then fails with a message such as "Wheels are required for x because building from source is disabled". The agent can't edit /etc, but it can still switch the setting off for one command (uv --no-config pip install x, PIP_ONLY_BINARY= pip install x), as it can run any command in its sandbox. So this guards against accidents and sloppy installs, not against an agent set on building; the network rules are the limit. A wheel can still run code when it is imported.

Other ways to lower the risk:

  • Ignore new releases: uv pip install --exclude-newer 2026-10-01 pillow skips everything uploaded after that date. Malicious releases are mostly found and removed within days, so a hijacked fresh release can't reach you.
  • Pin and check hashes: a requirements file with exact versions and hashes, installed with uv pip install --require-hashes -r requirements.txt (or pip install --require-hashes), rejects any file that differs from what you reviewed.
  • Choose well-known packages. Check the name (typosquats like pilllow), the maintainers and source repo on pypi.org, and the release history (a package made last week with one release is suspect). Popular packages are reviewed by many people, but they do get compromised now and then. OSV.dev lists known vulnerabilities and malware reports, pip-audit checks an environment against it, and deps.dev shows dependency trees.
  • Allow only the packages you approve (optional). Every install starts with a request to https://pypi.org/simple/<name>/, the package's index page (PEP 503) with links to its files, so a path rule on pypi.org can limit which packages the installer finds, by replacing access: read-only with rules like these (one per package and each of its dependencies; names are lowercase with hyphens, e.g. typing-extensions):
      - host: pypi.org
        port: 443
        protocol: rest
        enforcement: enforce
        rules:
          - allow: { method: GET, path: "/simple/pillow/" }
          - allow: { method: GET, path: "/simple/numpy/" }

The files themselves come from files.pythonhosted.org, whose paths hold only hashes and no package names, so that host can't be limited by package. The installer can't find other packages, but someone who knows a file's exact URL could still fetch it. This lowers the risk without removing it. Test the list in a sandbox before relying on it: a dependency you forgot fails the install, which is how you find it.

  • Remove the pypi rule from a copy of the policy for tasks that need no packages.

Replicate: models for images and video

The image can use Replicate to generate or edit images and video with hosted models, through an MCP server, skills and the API. The sandbox has no Replicate access until you give it a token:

  2. Create the provider: bin/provider.sh replicate. Once is enough; a new token goes in with bin/provider.sh --update replicate.

  • The MCP server replicate, registered by graphics-init only when the token is present. Things to know:

  • The token can spend your Replicate credit. A manipulated agent can run models on your account but cannot read the token or send it to other hosts: the proxy refuses the placeholder on every host outside the profile (credential_endpoint_mismatch).
  • Model output is generated content; check it before relying on it. Models and their outputs have their own licences and terms, separate from the Apache 2.0 of the skills and the MCP package.
  • Changes apply to new sandboxes. After editing providers/replicate.yaml, update the profile in the gateway (Update a profile, ID replicate) and create the sandbox again; a running one keeps the old rules. A denied call shows in openshell logs my-art | grep DENIED (e.g. DENIED QUERY … /v1/models before the method was allowed).
  • claude mcp list shows replicate as failed? Check that the sandbox was created after bin/provider.sh replicate (openshell sandbox exec -n my-art -- printenv REPLICATE_API_TOKEN prints a placeholder, openshell:resolve:env:...) and that the token is valid (api.replicate.com/v1/account returns 200 from python3).

The policy

policies/graphics.yaml is the terminal policy (vscode-terminal.yaml) plus network rules. The first is read-only (GET) access to PyPI, pypi.org and files.pythonhosted.org, for /usr/bin/python3 (which also covers pip) and /usr/local/bin/uv and uvx. The Replicate rules (replicate-files, replicate-outputs, replicate-stream, replicate-docs) are described under Replicate. Both apps work on local files and need nothing else. What Claude Code may do without asking is set in images/claude-graphics/managed-settings.json, installed as /etc/claude-code/managed-settings.json. These managed settings can't be changed by the agent. Rules are checked in the order deny, ask, allow:

What
Allowed (no prompt) Read, Glob, Grep, Edit, Write (the filesystem policy still limits where); all tools of the vectorcraft and photocraft MCP servers; the Bash commands ls, cat, head, tail, wc, file, mkdir, graphics-key, rm, node, and everything Python: python3 (including -m zipfile), .venv/bin/python, uv, uvx, pip; WebFetch of replicate.com; the Replicate MCP tools that cost nothing: reading and searching (get_* except get_account, list_*, search_models, download_files), create_models, create_files and cancelling (cancel_predictions, cancel_trainings)

Things to watch for

  • Gallery shows nothing or the page doesn't load? The forward is on (openshell forward list) but nothing listens in the sandbox if it was created from an older image or the agent hasn't started: check with openshell sandbox exec my-art -- python3 -c "import urllib.request as u; print(u.urlopen('http://127.0.0.1:3102/api/files').read())" and read /tmp/graphics-gallery.log. An empty page with "No images yet." means the server works and /sandbox has no images (images in hidden folders or other file types aren't shown).
  • Claude Code only. There is no agy or OpenCode variant.
  • The MCP root is /sandbox. Files elsewhere (e.g. /tmp) can't be opened or saved by the servers. The agent's other tools aren't limited by it, but by the sandbox's filesystem policy.
  • Existing sandboxes keep their old image. Create a new one after rebuilding, e.g. to update a version.
  • Size: the two CLI binaries are about 90 MB each, plus Python and uv.
  • Wheels only. A package with no wheel for arm64 or x86_64 and Debian's Python 3.11 can't be installed; see Installing Python packages.
  • Only PyPI, and Replicate if you set it up. npm, git clone from GitHub and other downloads are denied. A package that downloads something else when it installs or runs (a model, a binary) fails the same way.

Kiro Crew with Claude Code over ACP

Kiro Crew is an open-source persistent development workspace and agent orchestrator. In this setup, Kiro Crew runs its gateway service inside the sandbox and drives Claude Code over the Agent Client Protocol (ACP) as its agent harness (claude-agent-acp). For the other direction — an existing Kiro Crew outside the sandbox using Claude Code inside one as its ACP backend — see Claude Code as an ACP backend for an external Kiro Crew.

What it provides

  • Persistent Web Interface: A web dashboard served on port 5476 inside the sandbox (http://127.0.0.1:5476).
  • Claude Code via ACP: Kiro Crew communicates with Claude Code over the standardized Agent Client Protocol, keeping sessions, tools, and permissions governed inside the sandbox.
  • OpenShell Isolation: Claude Code API calls (api.anthropic.com and platform.claude.com) route through the attached claude provider with bearer token injection outside the sandbox.
  • Port forwarding: bin/sandbox.sh kirocrew forwards 5476 (the dashboard) and 9100 to 9109 to your host. Kiro Crew apps run a backend of their own on ports from 9100 up (the first app gets 9100, the next 9101), and their page loads it in an iframe from 127.0.0.1 in your browser, so those ports must be forwarded too. For an eleventh backend, run openshell forward start -d 9110 kirocrew.
  • App store: the policy allows the Kiro Crew app catalog (apps.crew.kiro.dev), clone-only access to GitHub and the PyPI and npm registries, so apps can be installed. Apps are third-party code that runs in the sandbox. For a sandbox with no network access, use the kirocrew-readonly profile (apps won't install or start).

Build and Run

  1. Build the image:
make claude-kirocrew
# or: podman build -t claude-kirocrew:latest images/claude-kirocrew
  1. Start the sandbox:
bin/sandbox.sh kirocrew

This creates the sandbox kirocrew using images/claude-kirocrew and policies/kirocrew.yaml (see profiles/kirocrew.env), forwards the ports above, and starts the Kiro Crew gateway. Use bin/sandbox.sh kirocrew-readonly for the same image with policies/kirocrew-readonly.yaml, which has no network access.

  1. Access the Dashboard: Open the sign-in link that Kiro Crew prints on start, but with 127.0.0.1 instead of localhost in it (http://127.0.0.1:5476?token=...). The forward is on 127.0.0.1 and the gateway doesn't redirect between the two names, so with localhost the session cookie doesn't match and you get "Session expired". kirocrew token doesn't work from openshell sandbox exec: the gateway doesn't accept that process as the local owner.

What the image does differently

  • No inner sandbox: Kiro Crew can't create user namespaces under OpenShell, so it has no sandbox of its own and the image sets KIROCREW_ALLOW_UNSANDBOXED=1 (and sandbox_allow_unsandboxed_exec in its config). The OpenShell sandbox is the only isolation boundary.
  • Proxy CA for git, pip and npm: Kiro Crew runs them with a scrubbed environment, and OpenShell's proxy terminates TLS with its own CA, so installing apps failed with certificate errors. The image points the system trust files, /etc/pip.conf and /usr/local/etc/npmrc at the bundle the supervisor writes at sandbox start. Outside OpenShell those links dangle and TLS fails closed.
  • Patched path pinning: Kiro Crew opens / and then each path component to pin a path, but OpenShell's Landlock baseline never grants / itself, so app backends, project skills and the pycache sweep failed with Permission denied: '/'. patch-unreadable-root.py makes those walks start at the first readable component, and fails the image build if Kiro Crew's code changes. Remove it once Kiro Crew or OpenShell fixes this.
  • Still blocked: Kiro Crew's telemetry endpoint (d175o3ylxqum0e.cloudfront.net), which you can leave blocked, and the Kiro CLI check, which logs kiro_prerequisite_required for some dashboard calls.

Remote Crew over SSH does not work

A sandbox running kirocrew cannot be the remote end of Kiro Crew's own Remote Crew feature (another Kiro Crew's Settings → Remote Crew, connected over SSH). openshell sandbox ssh-config <name> gives a working, non-interactive SSH entry (through openshell ssh-proxy, so no port opens on the sandbox), and Remote Crew's hub uses exactly that kind of entry to tunnel to the remote's loopback gateway and mint a dashboard token there. The mint step fails every time:

❌ Gateway refused the token request (HTTP 403): The gateway could not verify
this process as the local owner. Open the dashboard using its CLI login link
on the gateway host.

The gate (local_owner_bootstrap_allowed in Kiro Crew's member_memory_auth.py) requires the process asking for a token to share the gateway process's Linux user and mount namespace, or be a backend the gateway itself spawned. An SSH session into an OpenShell sandbox runs in a different namespace from the sandboxed kirocrew gateway process, so it is always refused — confirmed by testing kirocrew token over openshell sandbox ssh-config's entry, and by Kiro Crew's own pod feature, which hits the identical gate when a pod child tries to mint its own token and documents the same namespace rule verbatim. There is no config flag to relax it: a pod's version of this error says plainly that recreating anything does not change the verdict, and the only sanctioned fix is a caller running in the gateway's own namespace (pod up works around it by skipping the mint and having the gateway mint in-process instead — an option Remote Crew's SSH hub does not have).

Use the dashboard directly instead of Remote Crew: forward 5476 from wherever the hub lives to the sandbox — openshell forward start -d 5476 <name> run on that machine, or an SSH -L tunnel through openshell ssh-proxy — then open the sign-in link Kiro Crew prints on start with 127.0.0.1 in place of localhost (see the session-expired note above). You lose the Remote Crew switcher and cross-machine search, but the dashboard itself works the same.

Customizing

Provider profiles

A profile is a YAML file that you write yourself or download, and then import into the gateway. No command generates it.

  • Ready-made profiles are in the OpenShell repo. providers/openrouter.yaml is a local copy of one.
  • Custom profiles like providers/claude-code-oauth.yaml are written by hand. That one is based on the upstream claude-code.yaml, changed to use an OAuth token instead of an API key.

Fields

Field Purpose Example (claude-code-oauth)
id The profile's name, passed to --type when creating a provider claude-code-oauth
credentials The secret it needs, the environment variable it's read from, and how it's added to requests CLAUDE_CODE_OAUTH_TOKEN, sent as Authorization: Bearer
endpoints Hosts and ports the agent may reach. The credential is added only on requests to these api.anthropic.com:443, platform.claude.com:443
binaries Programs inside the sandbox that may use those endpoints /usr/local/lib/node_modules/@anthropic-ai/**
discovery Credentials that --from-existing looks for in the environment oauth_token
display_name, description, category, inference_capable Labels and metadata agent, true

Minimal example

id: my-agent
display_name: My agent
description: My agent with an API key
category: agent
inference_capable: true
credentials:
  - name: api_key
    description: API key for api.example.com
    env_vars: [MY_AGENT_API_KEY]   # read from the environment by --from-existing
    required: true
    auth_style: bearer             # sent as "Authorization: Bearer <key>"
    header_name: authorization
discovery:
  credentials: [api_key]
endpoints:
  - host: api.example.com
    port: 443
    protocol: rest
    access: read-write
    enforcement: enforce
binaries:
  - /usr/local/bin/my-agent        # the agent's path inside the image

Create a profile

  1. Start from a similar profile. Export one that's already in the gateway with openshell provider profile export <id>, or copy one from the OpenShell repo.
  2. Edit id, credentials, endpoints and binaries. To find the right binary path, run the agent once and check openshell logs <sandbox> | grep DENIED.
  3. Validate and import it, then check the result:
openshell provider profile lint   -f providers/my-agent.yaml
openshell provider profile import -f providers/my-agent.yaml
openshell provider profile describe my-agent
  1. Create a provider from it with openshell provider create --type my-agent ...

Update a profile

import and lint fail once the profile exists (custom provider profile '...' already exists). Use update instead. It needs the current resource_version from the gateway, so the commands below read it and add it to a temporary copy of the file. Set ID to the profile's id, e.g. claude-code-oauth or openrouter:

ID=claude-code-oauth
V=$(openshell provider profile export $ID | awk '/^resource_version:/{print $2}')
sed "s/^id: $ID\$/&\nresource_version: $V/" providers/$ID.yaml > /tmp/$ID.yaml
openshell provider profile update $ID -f /tmp/$ID.yaml
openshell provider profile describe $ID
  • Every provider of that type picks up the change; the provider records themselves aren't rewritten. Running sandboxes see the changed endpoints and binaries at their next sync, without a restart. A process that started earlier keeps the environment it started with, so start the agent again after changing a credential.

Sandbox policies

What a sandbox may access comes from three places:

  • The policy file (--policy) sets filesystem access. Without it, a sandbox gets OpenShell's built-in default.
  • The attached providers add network access to the hosts in their profiles.
  • Network rules you approve add more hosts, per sandbox.

Filesystem policy

This repo has these policies: this one, policies/example.yaml (below), policies/browser.yaml for the browser, policies/hyperframes.yaml for HyperFrames, policies/graphics.yaml for VectorCraft and PhotoCraft and policies/antigravity.yaml for Antigravity CLI. The one used everywhere is policies/vscode-terminal.yaml. It is the default policy plus /dev/pts and /dev/ptmx, so programs inside the sandbox can open terminals. VS Code's integrated terminal needs this; without it, it fails with forkpty(3) failed.

version: 1
filesystem_policy:
  include_workdir: true        # the workdir (/sandbox) is read-write
  read_only:
    - /bin
    - /usr
    - /lib
    - /proc
    - /dev/urandom
    - /etc
    - /var/log
  read_write:
    - /tmp
    - /dev/null
    - /dev/pts                 # added: terminals (VS Code's terminal)
    - /dev/ptmx                # added: terminals (VS Code's terminal)
landlock:
  compatibility: best_effort
  • read_only and read_write list the only paths the sandbox's processes may access. Everything else is blocked (enforced with Landlock).
  • landlock.compatibility is best_effort by default: if the kernel can't enforce your filesystem rules, the sandbox still starts without them and logs a high-severity finding. hard_requirement makes it refuse to start instead. OpenShell also adds baseline paths itself (e.g. /usr, /lib, /etc, /tmp) when the policy has network rules, and always protects /.openshell.
  • include_workdir: true makes the working directory (/sandbox, also $HOME) read-write.
  • There is no network_policies section, so network access comes only from the attached providers and approved rules.

Create your own:

  1. Start from policies/example.yaml (see Example policy with network rules), or from the default policy of an existing sandbox. --base leaves out the provider's network rules, and the sed drops the header lines before the YAML:
openshell policy get claude-agent1 --base | sed -n '/^version:/,$p' > policies/my-policy.yaml
  1. Edit the file, e.g. add paths to read_only or read_write. Only add what's needed: every path you add is something the agent can reach too.
  2. Network rules that every sandbox needs can go in a network_policies section, as in the example below. For a provider's own hosts, prefer the profile's endpoints.

Use it:

  • Pass it with --policy policies/my-policy.yaml when you create the sandbox.
  • Check what the sandbox got: openshell policy get claude-agent1 --base, or --full to include the provider's network rules.
  • Filesystem changes need a new sandbox. Filesystem rules are fixed when the sandbox starts. openshell policy set on a running sandbox loads the new version, but processes still can't access the new paths. Delete the sandbox and create it again with --policy.
  • Network changes apply right away. openshell policy set <sandbox> --policy <file> --wait hot-reloads network_policies without recreating the sandbox. policy set replaces the whole base policy, so start from openshell policy get <sandbox> --base and keep its filesystem part unchanged. Connections that were open under the old rules (keep-alive, tunnels, WebSockets) are closed, so clients have to reconnect. Without --wait, success only means the gateway accepted the change; with --wait, exit code 0 means the sandbox loaded it, 1 that it rejected it and 124 that the wait timed out. Removing paths or changing include_workdir, landlock or process is rejected on a running sandbox. If a new version can't be loaded, the sandbox blocks traffic until a valid policy loads (policy_validation_failure_mode, default fail_closed).

Example policy with network rules

policies/example.yaml is the terminal policy plus five network rules, as a starting point for your own policies. The paths are for the claude-sandbox image.

Rule Allows Blocks
python_docs Claude Code (claude.exe) reading docs.python.org, e.g. with its WebFetch tool Other programs, and anything but GET/HEAD/OPTIONS (access: read-only)
npm_registry node (which runs npm) downloading packages from registry.npmjs.org Writes such as npm login or npm publish
github_clone git clone and fetch from GitHub, via git's HTTPS helper git-remote-http git push (explicit deny_rules), and other git hosts
context7_mcp Claude Code using the Context7 MCP server (library docs): connecting, listing tools, and the tools resolve-library-id and query-docs Every other MCP method and tool
huggingface_mcp Claude Code using the Hugging Face MCP server: all standard MCP methods, and tools matching hub_repo_* Other tools, and hf_fs explicitly (deny_rules)

The structure of a rule:

network_policies:
  npm_registry:                    # rule name (any)
    name: npm-registry
    endpoints:                     # where to
      - host: registry.npmjs.org
        port: 443
        protocol: rest             # inspect each HTTP request...
        access: read-only          # ...and allow only GET, HEAD and OPTIONS
        enforcement: enforce       # block violations (the default, audit, only logs them)
    binaries:                      # who may connect
      - path: /usr/local/bin/node
  • Binaries: list the program that actually opens the connection, by its real path (check with readlink -f inside the sandbox). For npm that's node, and for git over HTTPS it's /usr/lib/git-core/git-remote-http. The DENIED lines in openshell logs <sandbox> show the path OpenShell saw. Globs work (/usr/lib/jvm/*/bin/java), and for a script you list its interpreter. OpenShell records a hash of each program the first time it connects, and denies it from then on if the file changes, e.g. after an upgrade inside the sandbox.
  • access or rules: access is a preset (read-only, read-write, full). rules allow specific methods, paths and query parameters, as in github_clone. An endpoint uses one or the other.
  • deny_rules always win over allow rules. Use them to make a ban explicit.
  • enforcement defaults to audit, which only logs a request that breaks the rules and lets it through. Set enforce to block it, as the examples here do. It only applies to the checks of protocol: rest/mcp endpoints; a connection to a host or binary no rule allows is always denied.
  • Some destinations are never allowed by a rule: loopback and link-local addresses (including the cloud metadata address 169.254.169.254), and, on exact-host and IP endpoints, the ports 2379, 2380, 6443, 10250 and 10255. Wildcard and host-less endpoints reach private addresses only through allowed_ips.
  • Without protocol, OpenShell only checks host, port and binary, and allows any request.
  • Credentials: a network rule never sends provider credentials. Those only go to the hosts in the provider's profile.

Remote MCP servers (context7_mcp, huggingface_mcp) use protocol: mcp. OpenShell then reads every MCP request and checks the method and, for tools/call, the tool name:

  context7_mcp:
    name: context7-mcp
    endpoints:
      - host: mcp.context7.com
        port: 443
        path: /mcp
        protocol: mcp
        enforcement: enforce
        mcp:
          versions: ["2025-03-26", "2025-06-18", "2025-11-25"]
        rules:
          - allow:
              method: initialize
          - allow:
              method: notifications/initialized
          - allow:
              method: tools/list
          - allow:
              method: tools/call
              tool:
                any: [resolve-library-id, query-docs]
    binaries:
      - path: /usr/local/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe
  • Two styles: list every allowed method, as in context7_mcp. Or set allow_all_known_mcp_methods: true and only restrict the tools, as in huggingface_mcp, which allows tool: "hub_repo_*" and denies hf_fs.
  • mcp.versions: the default is only 2025-11-25 (accepted: 2025-03-26, 2025-06-18, 2025-11-25 and 2026-07-28). Clients send initialize without a version header, which counts as 2025-03-26, so list that too.
  • Binary: Claude Code connects to remote MCP servers itself, so the binary is claude.exe. Add the server in Claude Code as usual, e.g. claude mcp add --transport http context7 https://mcp.context7.com/mcp.
  • Tool arguments aren't checked. An allowed tool can be called with any arguments.
  • Servers that need a login: put the token in a provider profile with the server's host as endpoint, and attach the provider. Never put tokens in a policy.
  • Claude Code asks every server for prompts/list and resources/list. With an explicit method list like context7_mcp, these appear as DENIED in the logs. That's harmless.

Network rules

A sandbox starts out mostly locked down. When the agent or another tool tries to reach a host that isn't allowed, the connection is denied and logged, and OpenShell proposes a rule that would allow it. Ask the agent to do what you want to allow (e.g. fetch a web page), then review the proposals. The examples use opencode-agent1.

  • Check the logs:
openshell logs opencode-agent1
openshell logs opencode-agent1 | grep DENIED

  • Every proposal is checked by OpenShell's policy prover before you see it. Logging and metrics

What happens in a sandbox is logged by its OpenShell supervisor: every connection it allows or denies, HTTP requests checked by a rule, SSH sessions, policy and setting changes. This page shows how to read those logs, watch the denials live, export everything to OpenTelemetry, and get the gateway's own metrics.

You want to Use
Look at a sandbox's log now openshell logs
See what's being blocked, live, across all sandboxes bin/watch-denied.sh
Keep the events, or send them to a log backend bin/otel-export.py
Look through exported events in the terminal bin/otel-view.py
Monitor the gateway itself bin/metrics-view.py, or Prometheus
Send metrics and events to an OpenTelemetry backend together observability/collector.yaml
Browse and graph metrics and events locally Grafana

Two kinds of logs

  • The shorthand log - one human-readable line per event, always on. This is what openshell logs shows, and what bin/watch-denied.sh reads.
  • OCSF JSON - the same events as complete structured records in the OCSF schema, off by default. This is what bin/otel-export.py reads. See OCSF JSON.

Reading the logs

  • The last 200 lines: openshell logs my-task
  • More, from the last 30 minutes: openshell logs my-task --since 30m -n 1000
  • Follow live: openshell logs my-task --tail
  • Warnings and errors only: openshell logs my-task --level warn This hides the policy events (DENIED and the like), which are logged at their own level, so don't use it when you look for blocked connections.
  • What was blocked: openshell logs my-task | grep DENIED
  • Without a name, openshell logs uses the last-used sandbox. --source sandbox or --source gateway shows only one side.
  • Limits: the gateway keeps only the last 2,000 log lines per sandbox, in memory, and loses them when it restarts. openshell logs doesn't show the agent's own output or what sandbox exec and SSH sessions print (use podman logs for the main process). For a durable record, export the OCSF JSON.
  • Line format: [time] [source] [level] [component] message, with the time in Unix seconds. Security events have the component [ocsf], an event type and an outcome:
[1791703672.439] [sandbox] [OCSF ] [ocsf] NET:REFUSE [MED] DENIED github.com [reason:policy_dns_ineligible]
[1791703672.552] [sandbox] [OCSF ] [ocsf] NET:OPEN [MED] DENIED /usr/lib/git-core/git-remote-http(0) -> github.com:443 [reason:transparent_tcp_policy_denied]
  • One blocked connection is two lines: NET:REFUSE when the name lookup is refused, and NET:OPEN when the connection is denied. The second one shows the binary that tried, by its real path. That path is what a profile's binaries list or a rule needs (see Network rules).
  • Requests that a rule checks at HTTP level are logged with the method and URL, e.g. HTTP:GET [INFO] ALLOWED GET http://api.anthropic.com:443/api/... [policy:_provider_claude engine:l7].

  • Only my-task (-s for short): bin/watch-denied.sh --sandbox my-task
  • Start with the last hour (default 1m): bin/watch-denied.sh --since 1h
  • Also show the known harmless denials: bin/watch-denied.sh --all
  • The DENIED lines themselves, with full binary paths: bin/watch-denied.sh --raw

OCSF JSON

Turn it on once, for all sandboxes. It applies within 10 seconds, without a restart:

openshell settings set --global --key ocsf_json_enabled --value true --yes
  • Check: openshell settings get my-task | grep ocsf
  • Off again: openshell settings set --global --key ocsf_json_enabled --value false --yes
  • Where it goes: the supervisor prints each event as an OCSF-JSON {...} line on its stderr, so the records are in podman logs openshell-supervisor-<sandbox id>, and bin/otel-export.py reads them from there. NVIDIA's docs also describe a file, /var/log/openshell-ocsf.YYYY-MM-DD.log, when file logging is available; OpenShell 0.1.3 with the Podman driver didn't write it here. It would be on a tmpfs inside the supervisor container and out of reach of openshell sandbox exec anyway.
  • Only from then on: events before the setting was turned on have no JSON record. The records are gone when the sandbox is deleted, so export what you want to keep.
  • A record carries the sandbox (container.name), the outcome (action, disposition), the destination (dst_endpoint), the process (actor.process), the rule that decided (firewall_rule) and a severity.
  • Schema version: v1.8.0 by default. ocsf_schema_version set to 1.1 or 1.3 downgrades the records for tools that need an older one (lossy, see the OpenShell docs).

Export as OpenTelemetry

bin/otel-export.py sends the sandboxes' security events (every allowed and denied connection, HTTP request, SSH session and config change) to any OpenTelemetry backend as OTLP logs. OpenShell has no OTel export of its own; its structured log is OCSF JSON, which the script converts.

  1. Turn on OCSF JSON, once:
openshell settings set --global --key ocsf_json_enabled --value true --yes
  1. Export to a file, or push to a collector:
    • All events so far: bin/otel-export.py --out sandboxes.otlp.jsonl
    • The last hour of one sandbox: bin/otel-export.py --out - --since 1h --sandbox my-task
    • Live: bin/otel-export.py --endpoint http://localhost:4318/v1/logs --follow
    • To a backend that needs a token: bin/otel-export.py --endpoint https://otlp.example.com/v1/logs --header "Authorization=Bearer $TOKEN" --follow
  • Where the events come from: the script reads the OCSF JSON records with podman logs of every openshell-supervisor-* container: all sandboxes, running or stopped. With --follow it picks up new sandboxes every 10 seconds. Events only start once the setting is on, and are gone when the sandbox is deleted.
  • What a record looks like: one resource per sandbox (service.name=openshell-sandbox, openshell.sandbox.name, openshell.sandbox.id, container.image.name). Each event keeps its own time, gets an OTel severity from the OCSF one, has the event's message as body, and carries the whole event flattened as ocsf.* attributes (ocsf.action, ocsf.dst_endpoint.domain, ocsf.actor.process.name, ...), plus event.name, server.address/server.port and process.executable.path. Filter denials on ocsf.action = Denied.
  • File format: one OTLP/JSON ExportLogsServiceRequest per line, the format of the Collector's file exporter. A Collector reads it back with the otlpjsonfile receiver.
  • Don't double-send: --follow starts with all events still in the logs. When restarting a live export, pass e.g. --since 5m.
  • The events say what the agent did: URLs, hosts and process names. Treat the export like the sandbox's contents when choosing where to send it.

Viewing the events

bin/otel-view.py is a minimal viewer for the terminal: one line per event (time, sandbox, severity, action, target, message), denials in red.

  • Live: bin/otel-export.py --out - --follow | bin/otel-view.py
  • A file: bin/otel-view.py sandboxes.otlp.jsonl
  • Only denials: bin/otel-view.py --where ocsf.action=Denied sandboxes.otlp.jsonl
  • One sandbox, every attribute: bin/otel-view.py --where openshell.sandbox.name=my-task -v ...

Gateway metrics

The gateway has a Prometheus endpoint, off by default. Its metrics are about the gateway: connected sandboxes, API calls, and the relays that carry exec, connect, SSH and port forwards into sandboxes. They don't count what agents do (use the OCSF events for denials per sandbox or host) or how much CPU and memory a sandbox uses (use podman stats).

  • Turn it on with the Homebrew service: put the port in ~/.config/openshell/gateway.env, which the service loads at start, and restart the gateway. The restart may drop open sessions (agents in a terminal, VS Code, SSH); the sandboxes keep running and reconnect to the gateway.
echo 'OPENSHELL_METRICS_PORT=9464' >> ~/.config/openshell/gateway.env
brew services restart openshell
curl -s http://127.0.0.1:9464/metrics

Without Homebrew, start the gateway with --metrics-port 9464 or the same environment variable. Delete the line and restart to turn it off. The endpoint listens on 127.0.0.1 only (--bind-address changes that for all listeners). The same can be set in gateway.toml as metrics_bind_address under [openshell.gateway]. The endpoint is plain HTTP without authentication, so keep it on loopback.

Metric Type What it tells you
openshell_server_supervisor_sessions gauge Sandboxes connected to the gateway
openshell_server_grpc_requests_total{method,code} counter Gateway API calls by method (ExecSandbox, ListSandboxes, GetSandboxConfig, ...) and gRPC status code
openshell_server_grpc_request_duration_seconds{method,code} summary API call latency
openshell_server_routed_request_attempts_total{operation,route,relay_kind,outcome,grpc_code} counter Relays into sandboxes (relay_kind ssh or tcp) and other routed calls, with outcome success, local_error or remote_error

Isolation on macOS

How well a sandbox is separated from your Mac when OpenShell runs on a Podman machine, what it's weak at, and how it compares to other ways of running containers.

Short answer: the VM is a strong boundary, but by default a Podman machine mounts the home folders read-write. A sandbox that escapes its container doesn't get into macOS, but it does get to read and change every file in your home folder.

The layers

From the agent outwards, with Podman's defaults on macOS:

Layer What it gives you
OpenShell sandbox A supervisor next to the workload makes every policy decision. The workload container has no network except its channel to the supervisor, so traffic can only leave through the policy proxy, with credentials only as placeholders. Landlock paths from the policy, seccomp, and a non-root user
Container Rootless Podman (crun): user namespaces, limited capabilities, seccomp, SELinux. A machine created with --rootful runs containers as root in the VM instead
Linux VM Fedora CoreOS on Apple's hypervisor (the applehv or libkrun provider), with its own kernel
macOS Only reachable through what the VM exposes: the shared folders and the Podman API

Check a machine: podman machine list shows the VM type, inspect prints false for rootless, info shows rootless, seccomp and SELinux, getenforce should print Enforcing, and the last command lists the host folders shared with the VM:

podman machine list
podman machine inspect --format '{{.Rootful}}'
podman info --format '{{.Host.Security}}'
podman machine ssh getenforce
podman machine ssh 'mount | grep virtiofs'

(The commands in this doc have no comments on the same line: zsh, the default shell on macOS, doesn't treat # as a comment when you paste commands, unless you've run setopt interactive_comments.)

Where it's weak

  • Your home folder is shared with the VM. podman machine init mounts /Users, /private and /var/folders read-write by default. So the VM protects your macOS processes, the Keychain and the network, but not your files. Whoever becomes the VM's user (core) can read ~/.ssh, ~/.config/openshell and a .env if you have one, edit ~/.zshrc, or plant code in any of your repos.
  • Root in the VM is one step away. core has passwordless sudo. Escaping the container is the hard part; after that there's nothing left in the way.
  • All sandboxes share one kernel. A kernel bug that lets an agent out of one sandbox gives it the VM, and every other sandbox in it. Escaping the hypervisor into macOS is much harder and very rare.

In practice the likelier risk is at the top layer: an agent sending data through hosts you allowed. That's what the network rules and credential placeholders are for. A container escape needs a kernel or runtime exploit, which is unlikely from a coding agent, but if it happens the shared home folder decides how bad it is.

A Podman machine with minimal host mounts

The biggest gain for the least effort: share only what OpenShell needs instead of your whole home folder. Sandboxes get your files through openshell sandbox upload and git bundles, not bind mounts, and podman build sends the build context over the API. The one host folder the Podman driver does need is its cache, ~/.local/share/openshell/podman-sandbox: the gateway unpacks the sandbox supervisor binary from the supervisor image there and bind-mounts it into every sandbox by its Mac path. Without it, sandbox create fails with statfs .../podman-sandbox/<hash>/openshell-sandbox: no such file or directory. The folder only holds that Linux binary, which macOS never runs.

  • Make sure there's enough free disk space first: df -h /System/Volumes/Data. Each machine has its own disk image with its own copy of every image, and building the images here takes about 8 GB. If the Mac runs out of space, the VM's filesystem shuts down and the build fails with server probably quit: unexpected EOF (the VM's console log, $TMPDIR/podman/openshell.log, then shows I/O error, dev vda).
  • Create a second machine. Passing --volume replaces the default mounts. This one shares the OpenShell cache, and an empty folder for anything you deliberately want to hand over (leave that one out if you don't need it). Mounts can't be changed later, only by creating the machine again:
mkdir -p ~/openshell-share ~/.local/share/openshell/podman-sandbox
podman machine init openshell \
  --volume "$HOME/openshell-share:$HOME/openshell-share" \
  --volume "$HOME/.local/share/openshell/podman-sandbox:$HOME/.local/share/openshell/podman-sandbox"
  • Set --cpus, --memory and --disk-size on init as for your current machine (podman machine list shows them).
  • Stop the current machine (only one can run at a time), start the new one, and check that only the two folders are mounted:
podman machine stop
podman machine start openshell
podman machine ssh openshell 'mount | grep virtiofs'
  • The shares are writable from the VM, even with :ro. With the applehv provider (tested with Podman 5.8), :ro on a volume is ignored. Keep openshell-share empty except for what you hand over, and treat anything in it as untrusted. Check it with podman machine ssh openshell "touch $HOME/openshell-share/x && echo writable". The double quotes make your Mac's $HOME used, which is also the share's path in the VM. Then delete ~/openshell-share/x.
  • Make it the default and restart the gateway, so it uses the new machine. Check with podman system connection list that openshell is the default: removing a machine can make another, stale connection the default again.
podman system connection default openshell
brew services restart openshell
  • Keep the VM's clock in step with the Mac's. This applies to any Podman machine on a Mac, not only this one. The VM's clock stands still while the Mac sleeps, and chrony in the VM often doesn't catch up: after the jump it distrusts its time servers (Jitter ... exceeds maxjitter in journalctl -u chronyd). Podman has no fix for this, and vfkit's own time sync on wake isn't turned on by Podman. Until the clock is right, new sandboxes fail with ContainerExited, and the supervisor container's log (podman logs openshell-supervisor-<id>) says session token was issued in the future: the gateway runs on the Mac and signs with the Mac's clock. bin/vm-clock.sh sets the running machine's clock from the Mac's when they differ by more than a second. Install it as a background job (launchd) that checks every 30 s:
bin/vm-clock.sh --install

It logs its corrections to ~/Library/Logs/openshell-vm-clock.log. Run bin/vm-clock.sh without arguments for a one-off check, and --uninstall to remove the job. The job runs the script from where the repo is, so run --install again after moving the repo.

  • The new machine has no images yet: make images, then check that a sandbox works with bin/sandbox.sh claude test -- -p 'reply with OK', and run make test. While a sandbox runs, podman --connection openshell ps lists its containers.
  • To go back: make the old machine's connection the default again (podman system connection list), stop openshell, start the old machine and restart the gateway.
  • Once the new machine works, remove the old one to get its disk space back: podman machine rm <old machine>. The disk image of a machine grows but never shrinks on its own.

Tested on macOS with Podman 5.8 and OpenShell 0.1.3: building the images, running Claude Code in a sandbox, and make test (browser, host MCP, HyperFrames). The VS Code connection hasn't been tested on this setup yet.

# Example sandbox policy: filesystem access plus network rules.
# A starting point to copy and adapt, e.g. to policies/my-task.yaml.
#
#   openshell sandbox create --policy policies/example.yaml ...
#
# The filesystem part is the same as vscode-terminal.yaml. The network rules
# come on top of the hosts the attached providers already allow (e.g.
# api.anthropic.com for the claude provider). Paths are for the claude-sandbox
# image (Dockerfile.claudecode); check others with `readlink -f` inside the
# sandbox, and the DENIED lines in `openshell logs <sandbox>`.
#
# Network rules can be changed on a running sandbox with
#   openshell policy set <sandbox> --policy <file> --wait
# Filesystem changes need a new sandbox.
version: 1

# Which paths processes in the sandbox may read and write. Everything else is
# blocked (Landlock).
filesystem_policy:
  include_workdir: true        # the workdir (/sandbox, also $HOME) is read-write
  read_only:
    - /bin
    - /usr
    - /lib
    - /proc
    - /dev/urandom
    - /etc
    - /var/log
  read_write:
    - /tmp
    - /dev/null
    - /dev/pts                 # terminals, needed by VS Code's terminal

landlock:
  compatibility: best_effort

# Which hosts each binary may reach. Each rule allows every listed binary to
# reach every listed endpoint. Anything not allowed here or by a provider
# profile is denied. A rule also covers processes started by its binaries.
network_policies:

  # 1. Read-only web access for Claude Code, e.g. its WebFetch tool.
  #    protocol: rest + access: read-only allows GET/HEAD/OPTIONS only, so the
  #    agent can read the docs but not send data to the site with POST.
  python_docs:
    name: python-docs
    endpoints:
      - host: docs.python.org
        port: 443
        protocol: rest
        access: read-only
        enforcement: enforce
    binaries:
      - path: /usr/local/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe

  # 2. Package installs with npm. npm is a Node.js script, so the process that
  #    connects is the node binary, not npm.
  npm_registry:
    name: npm-registry
    endpoints:
      - host: registry.npmjs.org
        port: 443
        protocol: rest
        access: read-only
        enforcement: enforce
    binaries:
      - path: /usr/local/bin/node

  # 3. git clone/fetch from public GitHub repos, but no push. Git's smart HTTP
  #    protocol fetches with GET .../info/refs?service=git-upload-pack and
  #    POST .../git-upload-pack, and pushes with the same requests for
  #    git-receive-pack. Only the fetch requests are allowed, and the push
  #    requests are also denied explicitly (deny rules win over allow rules).
  #    The HTTPS connection is opened by git's helper, git-remote-http
  #    (git-remote-https is a symlink to it).
  github_clone:
    name: github-clone
    endpoints:
      - host: github.com
        port: 443
        protocol: rest
        enforcement: enforce
        rules:
          - allow:
              method: GET
              path: "/**/info/refs"
              query:
                service: git-upload-pack
          - allow:
              method: POST
              path: "/**/git-upload-pack"
        deny_rules:
          - method: "*"
            path: "/**/git-receive-pack"
          - method: GET
            path: "/**/info/refs"
            query:
              service: git-receive-pack
    binaries:
      - path: /usr/lib/git-core/git-remote-http

  # Remote MCP servers (Streamable HTTP). protocol: mcp makes OpenShell read
  # each MCP request and check the method and, for tools/call, the tool name.
  # Tool arguments are not checked, so an allowed tool gets any arguments.
  # Claude Code connects to remote MCP servers itself, so the binary is
  # claude.exe. Add the server in Claude Code as usual, e.g.
  #   claude mcp add --transport http context7 https://mcp.context7.com/mcp
  # Don't put an MCP endpoint on the same host and port as an endpoint with
  # another protocol; OpenShell rejects that.
  #
  # mcp.versions: the MCP revisions the endpoint accepts. The default is only
  # 2025-11-25. A request without an MCP-Protocol-Version header counts as
  # 2025-03-26, and clients send `initialize` without it, so list 2025-03-26
  # too, plus the revisions the client and server negotiate.
  #
  # Servers that need a login: put the token in a provider profile with the
  # server's host as endpoint, like providers/claude-code-oauth.yaml, and
  # attach the provider. Never put tokens in a policy.

  # 4. MCP, explicit allow list: Context7 (library docs lookup, no login).
  #    Allows connecting (initialize), listing tools, and calling exactly two
  #    tools by name. Any other method or tool is denied. Claude Code also
  #    asks every server for prompts/list and resources/list; those show up as
  #    DENIED in the logs here, which is harmless. Add allow rules for them, or
  #    use allow_all_known_mcp_methods as in rule 5, to silence them.
  context7_mcp:
    name: context7-mcp
    endpoints:
      - host: mcp.context7.com
        port: 443
        path: /mcp
        protocol: mcp
        enforcement: enforce
        mcp:
          versions: ["2025-03-26", "2025-06-18", "2025-11-25"]
        rules:
          - allow:
              method: initialize
          - allow:
              method: notifications/initialized
          - allow:
              method: tools/list
          - allow:
              method: tools/call
              tool:
                any: [resolve-library-id, query-docs]
    binaries:
      - path: /usr/local/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe

  # 5. MCP, all standard methods plus a tool filter: Hugging Face Hub (no
  #    login needed for public search). allow_all_known_mcp_methods allows the
  #    standard MCP methods (initialize, tools/list, resources/read, ...), so
  #    they don't need to be listed. Tool calls are still limited to the
  #    allow rules: here every tool matching hub_repo_* (search and details).
  #    deny_rules win over every allow; here they block the file system tool
  #    hf_fs explicitly. Other tools, e.g. hf_whoami, are denied because no
  #    allow rule matches them.
  huggingface_mcp:
    name: huggingface-mcp
    endpoints:
      - host: huggingface.co
        port: 443
        path: /mcp
        protocol: mcp
        enforcement: enforce
        mcp:
          versions: ["2025-03-26", "2025-06-18", "2025-11-25"]
          allow_all_known_mcp_methods: true
        rules:
          - allow:
              tool: "hub_repo_*"
        deny_rules:
          - method: tools/call
            tool: hf_fs
    binaries:
      - path: /usr/local/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe

#
#   podman build -t claude-sandbox:latest images/claude-sandbox    (or: make images)

# Start it with `-- claude-start` instead of `-- claude`. On first start,
# claude-start copies /etc/claude-start.json to $HOME/.claude.json (/sandbox,
# which starts empty), which marks onboarding as completed. Images built on
# this one (images/claude-browser) can replace that file, e.g. to add MCP
# servers. Onboarding runs a connectivity check that bypasses the OpenShell
# proxy and is denied, so Claude Code would exit with
# "Failed to connect to api.anthropic.com: EACCES".
# For ACP (sandbox.sh --acp, acp_client.py --agent claude) use claude-acp-start.
FROM node:22-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends git ca-certificates \
 && rm -rf /var/lib/apt/lists/*
RUN npm install -g @anthropic-ai/claude-code @agentclientprotocol/claude-agent-acp
# No telemetry, error reporting or auto-updates. Their hosts are not in the
# claude-code-oauth profile, so the requests would only be denied.

# ACP adapter (claude-agent-acp): make it run the claude installed above, whose

ENV CLAUDE_CODE_EXECUTABLE=/usr/local/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe

COPY --chmod=755 claude-start claude-acp-start claude-acp-mkcwd-start /usr/local/bin/
